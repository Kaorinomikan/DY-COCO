## 四、已踩过的坑（写新功能前必读）

1. **虚拟滚动**：中控台 DOM 里只有 8~11 个商品节点，真实有 100+。
   绝不能靠数 DOM 节点判断序号或总数，必须按行距算位置。

2. **商品行 class 是空字符串**：任何依赖 class 名定位商品行的做法都会失败。

3. **嵌套滚动**：中控台只滚内层容器，浏览器窗口不动，用户完全看不到变化。
   必须遍历所有可滚动祖先。

4. **平台会改版**：抖店是 React SPA + Garfish 微前端，class 名带构建哈希、
   每次发版都会变。**优先用「可见文字 + 结构特征」，不依赖具体 class**。

5. **诊断优先于猜测**：写个自测按钮输出真实数据，比猜三次管用。
   调试面板的「扫描页面按钮」就是为此存在。

6. **隔离世界**：内容脚本的 `window` ≠ 页面 `window`。
   挂到 window 上的函数在 DevTools 控制台里调不到，只能用 `console.log` 输出。

7. **不要用定时器猜时机**：状态依赖要挂在真实事件上（如 DOM 插入成功的回调）。

8. **注入顺序有依赖**：`manifest.json` 中 `anchor.js` 必须排第一，
   因为它创建状态条容器。若 `anchor.js` 缺失，`ensureStatusBar()` 会兜底重建，
   但探针日志会丢失。

9. **函数改名要同步调用点**：`main.js` 曾把 `boot()` 改名为 `tryBoot()` 但漏改调用点，
   导致切回列表页时静默失败、按钮不重新注入。这类问题不报错，只能靠审阅发现。

10. **URL 正则转义陷阱**：`anchor.js` 的 URL 正则曾被误转义成
    `/^https:\/\/////fxg//.jinritemai//.com…` → 永远匹配失败，
    等于「页面匹配」判断从未生效。因按钮注入走 `manifest.json` 的 `matches`，
    症状完全没暴露出来。**改正则后必须实际验证匹配**。

11. **路径即身份**：扩展目录路径变了= 浏览器按新路径算扩展 ID =
    旧扩展残留且无法卸载，且用户设置（如 `dybDebug`）全部丢失。
    **覆盖更新必须解压到同一个目录。**

12. **扩展无法“直接”替换自身文件**：MV3 中没有任何文件系统 API。
    **但不等于做不到**——2026-10-10 实测后确认，唯一出口是
    File System Access API（详见「三之二、更新机制」）。
    除此之外的路径（CRX + update_url、`chrome.downloads`、
    `file://` 读写、外部更新器 / 原生消息宿主）全部被平台限制
    或用户要求否决，不要再走一遍。

13. **⚠️ manifest 的 `version` 字段不能含字母——含了扩展直接加载不了。**
    Chrome 强制要求 `version` 是 1~4 个点分整数（每段 0~65535），
    不允许字母或 `-beta` 之类的后缀。Chrome 官方原话：
    "No suffixes like `-beta` — Chrome rejects them."
    2026-10-10 把版本号改成 `"20261010V1"` 后，扩展**完全无法加载**，
    而且 Chrome 报错**不会明确指向版本号格式**，极易误判成图标或路径问题。
    现在的规范 `26.10.10.1` 已天然满足要求。
    改版本号前，务必先跑格式校验，或用下面的真机校验法验证。

    **可复用的真机校验法**（比只看 JSON 合法性强得多）：
    ```bash
    # 360 极速浏览器X 的路径
    CHROME="C:/Users/79412/AppData/Local/360ChromeX/Chrome/Application/360ChromeX.exe"
    # 在临时目录做，避免污染工程
    "$CHROME" --pack-extension="C:\temp\test\DY-COCO" --no-message-box
    ```
    - 成功 → 生成 `.crx` + `.pem`，exit=36
    - 失败 → 无产物，exit=22

    ⚠️ 该命令会生成 **`.pem` 私钥文件**，必须在临时目录里做、用完立即删除，
    绝不能留在工程目录或入库。

    另一个小陷阱：脚本里读版本号要用精确匹配 `grep '"version":'`，
    不要用 `grep '"version"'`——后者会把 `manifest_version` 等字段一起命中。

14. **版本号绝对不能当字符串比大小。**
    `"26.10.9.1" > "26.10.10.1"` 在字符串比较下成立，
    会导致**真正的更新被漏掉**（9 被当成比 10 大）。
    必须逐段转整数比较，见 `src/shared/gitee.js` 的 `compareVersion()`。

15. **popup 一失焦就被浏览器关闭，JS 上下文随之销毁。**
    由此有两条硬约束：① 确认框不能用 `window.confirm`
    （原生模态可能触发失焦关闭）；② 任何会弹系统对话框的操作
    （目录选择、文件授权）**必须放在独立窗口/标签页**里做，
    在 popup 内做必然中途失败。

16. **标签归档的完整性取决于“文件是否真的入库”。**
    打标签时若 `icons/` 还没 `git add`，归档包里就没有图标，
    覆盖更新后 manifest 引用不到图标 → **扩展直接加载失败**。
    所以更新页有「必需文件闸门」，发版前也必须确认
    `git status` 里没有未跟踪的必需资源。

17. **File System Access 的目录写权限不跨浏览器重启保留。**
    Chromium 只对“已安装的 PWA”做持久化授权。
    句柄可以存 IndexedDB 复用，但重启后需要用户点一次授权按钮，
    **不需要重新翻目录**。这是平台安全模型决定的，不要试图跳过。

18. **不要把「拖 zip 进扩展页」当作分发方式**（虽然确实能装上）。
    每次拖入都生成新的随机目录 → 新扩展 ID → 设置丢失 + 出现两个同名扩展。
    详见「三之三、分发与安装」。要验证更新机制，扩展必须装在**固定目录**里。

19. **给 cmd 跑的 .bat 必须是 GBK 编码，换行必须是 CRLF。**
    UTF-8 的中文在 cmd 下直接变乱码；LF 换行会让 `goto` 标签跳转在部分环境出错。
    开头加一行 `chcp 936 >nul`，保证用户系统代码页异常时也能正常显示。
    仓库内保存 UTF-8 源文件便于阅读，转码交给 `scripts/make-dist.py`。

20. **`%~dp0` 是 bat 自己所在目录（含尾部反斜杠）。**
    因此用户即便在压缩包预览窗口里直接双击也能工作（Windows 会先解到临时目录
    再运行），但正式说明仍要求先完整解压——避免用户误以为「打开压缩包就算装完了」。

21. **Windows 下的中文路径，不要靠内联 shell 命令传递。**
    在 git bash 里调 `cmd /c "含中文的绝对路径"` 容易被安全策略拦下，
    或因为转义被改写。写成 .bat / .py 脚本文件再调用，比内联命令可靠得多。

22. **Gitee 的 Release 接口与 GitHub 不一样，不要照搬记忆。**
    上传附件用 `release_id`（不是 tag），请求体必须是 `multipart/form-data`
    且字段名 `file`（用 JSON 会失败）；按 tag 查发行版在**不存在时返回
    200 + `null`**，而不是 404。逐条实测见「三之三、发行版上传与下载渠道」。

23. **不要把扩展目录放到 `C:\Program Files`**（用户 2026-10-10 提议过，已实测否决）。
    实测：`icacls "C:\Program Files"` 对 `BUILTIN\Users` 只给 `(RX)`，
    普通权限 `mkdir` 直接 Permission denied；**即使以管理员身份把目录建出来，
    继承下来的 ACL 仍是 Users 只读**，而浏览器进程以普通用户权限运行 →
    File System Access 的 `createWritable()` 必然失败 → **自动更新整套机制报废**。
    想救只能装完再跑 `icacls /grant`，那在 Program Files 上极易被安全软件拦。
    根本矛盾：加载已解压的扩展是「按用户的绿色程序」，而 Program Files 的语义是
    「系统级、防改动」—— 自动更新**必须**可写，两者不可兼得。
    对照：`C:\` 根目录对 `Authenticated Users` 有 `(OI)(CI)(IO)(M)`（可写），
    所以 `C:\DY-COCO` 免提权即可创建和写入。

24. **Gitee 匿名接口有限流：未登录 60 次/小时，超了返回 403 `Rate Limit Exceeded`。**
    2026-10-10 真机验证「检查更新」时撞上，弹窗直接显示红字，看着像插件坏了。
    同一接口**带上私人令牌返回 200**（5000 次/小时），证明账号、仓库、接口全都正常，
    纯粹是频次打满（当晚发布 + 调试 + 反复点击累积）。
    响应头里的 `BDWAF-Request-ID` 是 Gitee WAF 的标记，可用来确认是限流而非封禁。

    **教训**：把「检测新版本」这种用户随时可能触发的动作放在匿名 API 上，
    等于给功能埋了一颗不定时炸弹。修法是把它移出 API —— 见「三之二、数据源与接口」。

25. **`fetch(..., { redirect: 'follow' })` 的落点不可控，解析必须宽松。**
    同一条 `…/releases/latest`：curl 停在 `…/releases/tag/<tag>`，
    而 Node 的 fetch 被内容协商导去了 `…/repository/blazearchive/<tag>.tar.gz`。
    第一版代码把 `\/releases\/tag\/` 写死了，于是解析不出来、检测直接报错。
    最终改成 `/(?:releases\/tag|blazearchive)\/(v?\d+(?:\.\d+)+)/i`，
    **两种落点都认**（共同点是 URL 里都带着版本号）。
    改这类解析前先实测两种落点，不要凭一次结果下结论。

    另：**发行版不存在时 `…/releases/latest` 返回 404**（实测）。
    所以检测依赖「仓库里至少有一个 Release」——
    删发行版会让检测降级到 API，而 API 又可能限流。**删发行版要三思。**

26. **⚠️ 只改 `src/shared/` 而不动 `service-worker.js`，后台代码不会更新。**
    MV3 的 Service Worker 脚本包按**主脚本自身的内容**缓存，
    `importScripts` 引入的文件不参与缓存键判定。
    表现为「磁盘已是新版、弹窗版本号也是新版，但检查更新仍报旧代码的错误」——
    2026-10-10 真机撞上过，整整误导了一轮排查方向（详见
    「三之二、Service Worker 脚本缓存」，那里有完整的现象与实证过程）。

    **做法**：改动 `src/shared/` 时，把 `src/background/service-worker.js` 里的
    `var DYC_BUILD = '<版本号>+swN';` 的 N 自增。
    `publish.sh` 已加机械闸门：`src/shared/` 有改动而 `DYC_BUILD` 的值没变 → 直接中止发布。

27. **发布版和「商家实际会拿到的更新」可能不是同一件事，验证时要分开想。**
    26.10.10.4 那次：分发包本身完全正确，但**通过自更新交付时修复送不到**
    （原因就是第 26 条）。所以「新用户装 .4 没问题」与
    「老用户升 .4 能拿到修复」是两个独立结论，不能互相推断。
    判断某个修复是否真的送达，要看**目标机器实际运行的代码**，不是看仓库或包里的内容。

28. **Gitee 匿名 API 的限流是 IP 级的，不是仓库级的。**
    现象：本仓库所有 API 端点 403；同期 `mirrors/nginx`、`mirrors/redis`
    这类**别人的公开仓库**也 403。说明是本机出口 IP 的匿名额度被整体打满
    （未登录 60 次/小时，见第 24 条），与仓库、令牌、账号都无关。
    排查时**一定要拿别的公开仓库做对照**，否则会误判成「我们仓库被封」而查错方向。
    结论：**任何走 API 的运行时路径都不可靠**，能不用就不用。
    26.10.10.6 把下载也搬到 raw 通道后，更新链路已是 0 次 API 调用。

29. **生成物必须配一道「与代码一致」的机械闸门，不能靠人记。**
    `update-manifest.json` 记录 23 个文件的 sha256,扩展按它校验下载内容;
    它由脚本生成、随代码提交。于是「改了代码忘了重新生成清单」会让
    **所有商家更新失败**，报错却是「内容校验失败：xxx」——
    看起来像文件损坏，极难定位。这类「生成物 vs 源」的漂移问题必须机器拦。
    `publish.sh` 里的做法：重新计算一遍磁盘哈希与清单比对，不一致直接中止发布。
    与第 26 条（改了 `src/shared/` 必须 bump `DYC_BUILD`）是同一思路的两道闸门。

30. **清单哈希必须对应「仓库 blob」，不是「工作区文件」—— Windows 行尾坑。**
    本机 `core.autocrlf=true`，实测 `git ls-files --eol` 有 4 个文件处于
    `i/lf w/crlf`（仓库里是 LF、工作区是 CRLF）。若清单按工作区字节算哈希，
    这几个文件就会与仓库内容不符，商家更新时校验失败 ——
    而报错是「内容校验失败：xxx」，看着像文件损坏，极难定位。
    两道防线：
    ① `scripts/make-update-manifest.py` 的 `file_bytes()` 对**文本文件**做 LF
       归一化（模拟 git 的存储行为），`size` 与 `sha256` 都用归一化后的结果 ——
       扩展侧 `fetchRawFile` 会拿清单里的 `size` 校验长度，两者必须同源；
    ② `.gitattributes` 把扩展本体（`manifest.json` / `src/**` / `icons/**`）
       的行尾锁成 LF，范围刻意不覆盖 LICENSE 等 Gitee 网页直接编辑过的文件。
    **判断清单对不对的方法**：逐条比对 `git show HEAD:<path>` 的字节。
    发布前必须做这一步，不能只看 `--check` 通过 ——
    闸门和清单都基于同一份工作区，一起错的时候闸门不会报。

31. **Gitee 的「标签」与「发行版」是两样独立的东西，检测别只认发行版。**
    背景：Gitee 上 git tag 与 Release 各自独立存在。检测若读
    `…/releases/latest`，就**看不见「只推了标签、没建发行版」的版本**。
    实测本仓库（2026-10-10）同一时刻：`/releases` 页面 4 个版本，
    `/tags.atom` 9 个（多出的 5 个正是没有发行版的 v1.0.0~v1.1.0）。
    真机表现：用户推了新标签，扩展弹窗仍写「已是最新版本」，
    怎么点都一样 —— 看起来像「一直读旧缓存」，实际是**根本没看见**。
    为什么容易撞上：`publish.sh` 是**先推标签、最后才建发行版**这个顺序，
    令牌失效/被限流时就会停在中间，留下「标签已推、发行版没建」的半发布状态。
    处理（26.10.10.7）：
    ① 检测主通道改读 `…/tags.atom`（网页通道、0 次 API、含全部标签），
       `…/releases/latest` 降级为兜底；
    ② `publish.sh` 加 `--preflight`：推送**之前**探通接口，不通就中止，
       绝不进入半发布状态；
    ③ `publish.sh` 加 `--audit`：发布**之后**核对「标签 / 发行版 / 附件」
       三者齐全 —— 光有发行版不够，商家真正下载的是附件。
    教训：**「仓库里有这个版本」与「客户端能发现这个版本」是两个独立结论**，
    中间隔着发布是否完整、检测通道看得见什么。

32. **判断「附件传没传上」要探测直下链接，不要读附件列表接口。**
    事故（2026-10-11 发布 26.10.10.8）：`gitee-release.py` 的附件复核与
    `--audit` 都调 `list_assets()` 读
    `/repos/{o}/{r}/releases/{id}/attach_files`。那次调用**没带令牌**
    → 走匿名接口 → 撞上限流返回 `403 Forbidden (Rate Limit Exceeded)`
    → `isinstance(obj, list)` 为假 → 返回空列表 → 脚本报
    「发行版里没有附件，商家按直下链接会 404」并 exit 1。
    **而实际上附件早传成功了**：直下链接 HTTP 200、86441 字节，
    sha256 与本地包逐字节一致。于是发布**明明成功却显示失败**，
    验收标记不清理，人也会以为要重发。
    处理：
    ① `list_assets()` 强制带 `access_token`（匿名额度约 60 次/小时且按出口 IP 计，
       带令牌 5000 次/小时，不会撞）；
    ② 判据换成 **HEAD 探测直下链接**（`probe_download()`）——
       它验的正是「商家点开能不能下载」这个最终结果，且**不占 API 额度**
       （走 gitee.com 普通路由，不是 `/api/v5`）；
       实测附件在 → 首跳 302 且 Location 含 `attach_files/`；不在 → 404。
    教训：**闸门的判据要选「离最终结果最近」的那一个。**
    「附件列表接口说没有」与「商家下不到」不是一回事；
    前者还会因为限流、缓存、刷新延迟而说谎。

33. **Gitee 上旧的发行版（Release）会消失，别把「历史发行版一直在」当前提。**
    现象（2026-10-11）：发布 26.10.10.8 时，`publish.sh` 内的 audit 显示
    `v26.10.10.3/.4/.5/.6/.8` 五个版本**都有发行版**；几分钟后再查，
    `v26.10.10.3/.4/.5` 的发行版**已不存在**（按 tag 查返回 `null`，
    直下链接 404），只剩 `.6` 和 `.8`。
    即**同步的窗口内还能查到，之后就没了** —— 疑似 Gitee 社区版对
    发行版数量有限制，创建新发行版后把最旧的清理掉（具体规则未确认，
    帮助中心未见明文；也有可能是异步清理）。
    **对项目的影响与应对：**
    · 商家**只用最新版的直下链接**，所以实际影响很小；
    · **已装旧版的商家升级不受影响** —— 自更新走 raw 通道（`raw/<tag>/…`），
      完全不碰发行版（这正是 26.10.10.6/.7 改造的价值）；
    · 但**旧版直下链接会 404**，若曾把 .3/.4/.5 的链接发给过商家，
      那个链接现在失效了，需要重发最新链接；
    · `--audit` 里「历史标签缺发行版」那类提示**可能只是这个清理造成的**，
      不代表本次发布有问题 —— **本次版本本身要看直下链接探测是否通过**。
    · **结论（2026-10-11 用户决定）**：既然发行版会被 Gitee 自动清理、而
      自更新链路完全不依赖它，用户明确要求**此后不再创建任何发行版** ——
      见个性化要求第 8 条。本坑保留为「为什么会有这个决定」的原始依据。

34. **MV3 的 `chrome.storage.local.get()` 不传回调时返回 Promise，
    取它的属性永远是 `undefined`。**

    ```js

    if (r && r.dybDebug) return true;   // ← r 是 Promise，这句永远不成立
    ```

    危害很隐蔽：**不报错**，只是永远走不到 storage 分支、退回 URL 判定。

    这个 bug 因此活了很久没被发现。

    要么传回调，要么 `.then()`，**不要直接取属性**。

41. **「当前页在哪」不能赌 `currentWindow` —— 国产壳会把它指到扩展自己的弹窗上。**
   2026-10-13 用户报「反馈又变回独立小窗了」，并怀疑是上一版推送把功能改了回去。
   逐版本核对的结果是：**推送根本没碰过反馈** —— `v26.10.13.1` 与 `v26.10.13.2` 的
   `src/feedback/` 逐字节相同（`git diff --stat` 为空），Gitee 上两个 tag 的提交对象
   也与本地一致（`git ls-remote` 比对）。问题出在注入判据本身：
   ```js
   var tabs = await chrome.tabs.query({active: true, currentWindow: true});
   if (!tab || !tab.id || !/^https?:/i.test(tab.url || '')) throw new Error('当前页面无法注入');
   ```
   ① **360 极速浏览器X 把扩展弹窗渲染成独立窗口**：popup 一开，`currentWindow` 就
      指向弹窗自己，它的活动标签是 `chrome-extension://…/popup.html` → 正则不匹配
      → 判定「无法注入」→ 直接开独立小窗。而用户点反馈的**唯一入口就是 popup**，
      所以在这台机器上浮层从来没生效过；「上一版还能用」是记忆偏差 —— 那版也没生效。
   ② 老内核上 `tabs.query` / `scripting.executeScript` 的 **Promise 形式**可能缺位，
      `await` 拿到 `undefined`，会走进同一条兜底路径。判据不能建在内核版本差异上。
   修法（`service-worker.js`）：
   - `chromeCb(fn, timeout)` 把 callback API 统一包成 Promise（带超时，防回调不触发挂死）；
   - `listCandidateTabs()` 遍历**所有窗口**挑标签，`type === 'popup'` 一律跳过，按
     「焦点窗口的活动标签 > host_permissions 覆盖的站 > 最近访问过」排序；
   - `injectPanelScript()` 优先 `scripting`，缺失时回退 MV2 的 `tabs.executeScript`；
   - 兜底开小窗时把失败原因经 URL 的 `why` 参数带过去，**小窗顶部黄条显示** ——
     下次再降级能直接看见原因，不用猜。
   证据（`.tmp/verify-feedback-panel.js`，真实 Chromium，同一场景跑新旧两版）：

   | 版本 | SW 返回 | 页面里的浮层 | 独立小窗 |
   |---|---|---|---|
   | 旧（推送版） | `{"ok":true,"injected":false,"error":"当前页面无法注入"}` | 无 | **开了** |
   | 新（本次修复） | `{"ok":true,"injected":true}` | 有 `#dyc-fb-host` | 没开 |

   教训：**「用户正在看哪个页面」这种概念在浏览器壳层差异下不可靠**。国产壳把弹窗
   做成独立窗口、把新标签做成独立进程都是常见改法；凡是要拿「当前页」，就别赌
   `currentWindow` 的语义 —— 要么遍历所有窗口自己挑，要么从用户动作里传递 tabId。

44. **隐藏「会被平台按尺寸/可见性预留空间」的区块，用 `opacity:0`，别用 `display` 或 `visibility`。**
    （2026-10-14 两轮报障 + 真机实测后定稿）
    现象：抖店商品列表页开启「隐藏页面元素」后，商品表右侧平白多出一条白槽
    （表头灰底提前断掉、最后一列内容整体左移），整个商品界面像是「往左缩了一个红框」；
    关闭拦截（助手可见）时一切正常。
    **真机实测**（浏览器探针读 `fxg.jinritemai.com/ffa/g/list` 的真实 DOM）：
    - `.index_wrapper__3UiS6` 只命中 **1 个**元素，是 `position:absolute` 的浮动层
      （父级 `position:fixed`、56px 宽的宿主）—— **它根本不在布局流里**，
      所以第一版「右轨占位塌了、盒子消失触发重排」的解释是**错的**；
    - 页面表格是 `ecom-g-table`（ant 系）：`table-layout:fixed` + 右侧粘性「操作」列，
      **列宽是固定值**；表头那道灰来自 TH 的 `background:rgb(248,249,250)`。
    根因（推论，与实测吻合）：平台用 JS **按右轨的尺寸或可见性预留**右侧空间。
    隐藏手法一旦被它察觉，预留就变，而列宽是死的 ⇒ 右边空出一条。两个已知暴露面：
    - `display:none` —— 元素尺寸量到 0，任何按尺寸算的预留都会跟着变；
    - `visibility:hidden` —— 尺寸虽在，但 **computed visibility 变成 hidden**，
      平台读一眼样式就知道它被藏了。
      （实测纠正：`checkVisibility()` 默认**不**检查 visibility，对它仍返回 `true` ——
      暴露面是 computed 值本身，不是这个 API。第二版就是栽在这一步。）
    口径：`DYC_HIDE_TARGETS` 每项带 `mode` ——
    - `'display'`：纯浮层、平台不关心它，直接摘掉最干净；
    - `'opacity'`：**会被平台按尺寸/可见性预留空间的区块必须用这个** ——
      `opacity:0` + `pointer-events:none`（连子元素一起钉：它是可继承属性，
      但子元素可能自己写 `auto`），**display／尺寸／computed visibility 三项检测面全绿**；
      不必给子元素加 `opacity` —— 父级 `opacity:0` 管整棵子树。
    抖店侧两条目标都是 `opacity`；中控台的助手是纯浮层，保持 `display`。
    证据：`.tmp/verify-hide-rail.js` **57/57**（真实 Chromium：`display` 下白槽出现、
    `visibility` 下 computed visibility 变 hidden、`opacity` 下布局与「没开拦截」逐像素
    一致且零新增重排；另含点击穿透、两个反向对照、规则文本、三域名页面匹配）。
    ⚠️ 仍待真机验收：上面「平台按尺寸/可见性预留」是**推论**，`opacity` 版在真机上的
    效果要用户复测；`.tmp/probe-shop-ab2.js` 是备好的一键 A/B 探针
    （基线／display／visibility／opacity／挪出屏幕 五种状态各量一遍，哪个与基线一致就用哪个）。

45. **往 `DYC_HIDE_TARGETS` 加新项，必须同时处理「老用户清单里没有它」这件事。**
    （2026-10-18 加「右侧客服/反馈浮条」时定）
    坑在哪：勾选清单存的是 id 数组，老用户 storage 里**已经有**一份清单。
    只把新项写进登记表，弹窗会多出一个**未勾选**的复选框 —— 用户以为「默认勾选」没生效，
    实际是永不会被自动勾上（代码只在他手动勾、点保存后才写清单）。
    两种错解都要避开：
    - 只改登记表不迁移 ⇒ 新项对老用户永远默认关；
    - 「缺什么补什么」⇒ 把用户**亲手取消**过的旧项复活。
    现行解法：单开一个 `dybHideSeen` 键记「用户见过哪些 id」。
      见过 + 不在清单 = 他取消的，**不补**；从未见过 = 本次新加的，按 `defaultOn` 补勾一次；
      补完把 ids 记进 seen，此后回到「清单说了算」。首次迁移没有 seen 记录时也补一次
      （用户对新增项的明确要求是「装好即隐藏」，代价仅是可能复活他取消过的旧项，取消即可）。
    配套三条：
    - 选择器允许写**逗号列表**（如 `[class*="summon"], [id*="summon"]`），但前缀必须
      用 `prefixed()` **逐分句**加 —— `'html body ' + 整串` 会让逗号后那段掉一档特异性；
    - 类名不确定时用**属性子串匹配**（`[class*="xxx"]`）而不是猜精确类名：
      同 SDK 挂出来的节点一般共享前缀。前提是**有结构证据**（如页面结构报告里
      出现 `div.summon-iframe-contrainer` / `style#summon-sdk-style`），不是凭空猜；
    - **几处「长得像、性质相同、只是类名不同」的浮条，合并成一个清单项**，不要按页面拆成
      多项（用户 2026-10-18 原话：「每个网页显示的差不多，但是有点不一样」）。
      给该项配 `barScan` 通用扫描兜底，页面再多也不用改弹窗。
        判据（全部满足才算）：贴右缘（距右边 ≤60px）+ 窄（≤160px）+ 竖条（高/宽 ≥1.05）
        + 高 ≥90px + 命中 ≥2 个关键词（客服/反馈/举报/调研/问卷/意见/帮助/移动）+ 位于浮层
        （自身或 3 层内祖先为 fixed/absolute）。命中后打 `data-dyc-hide-bar`，由 CSS 隐藏。
        ⚠️ **必须先做几何判定、再在通过者里取最外层** —— 反过来会先选中 body / #root
        这类包装（它们的 textContent 同样含关键词、子元素也不多），而包装尺寸是 0×0 或整页，
        判定必然失败，浮条本体反被漏掉（2026-10-18 自测实测抓到，改序后 3/3 命中）。
        ⚠️ 扫描的开销必须三层约束：深度上限 + 节点预算 + 只在文本预筛通过的少数候选上读布局；
        MutationObserver 回调里只排一次防抖任务，不做任何查询。
        ⚠️ 防抖要配**最长等待**上限：大屏/中控台这类页面 DOM 几乎不停在变，纯防抖会被
        无限推后（永远等不到静默窗口），浮条迟迟不藏。现行 `BAR_DEBOUNCE=400` +
        `BAR_MAX_WAIT=1200`（从排队开始计时，到点必扫）。
    自测：`.tmp/verify-feedback-bar.js` **48/48**（真跑 flags.js + hide-elements.js，
    覆盖 5 种存档形态的补勾判定、4 类页面拼出的 CSS 文本、三处浮条形态各被扫到且
    同页 4 个反例不被误伤、manifest 条目组合与排除项）。
46. **「补插」不许塞进「接管早退」里 —— 幂等标记会把修复路径一起关掉。**
    （2026-10-19 修 #97「搜索框旁【全能搜索】按钮消失」时定）
    坑在哪：`takeOverInput` 原来的第一行是「见到 `data-dyc-search=1` 就 return」。

    而且**刷新页面才恢复**（刷新后 input 是新节点，标记没了）。

49. **自动切页 / 自动滚动这类「替用户动手」的功能，三条硬规矩。**
    （2026-10-20 定，来自直播明细那次）
    - **判据一律用 `event.isTrusted` 分流**：浏览器产生的事件为 `true`、
      我们 `dispatchEvent` 造的为 `false`。这一条天然把「用户点的/滚的」与
      「我们点的/滚的」分开，不需要额外标志位；老内核上若恒为 `undefined`，
      **一律视为用户操作**（宁可少自动一次，也不要跟用户抢）。
    - **滚动不许用 `scrollIntoView`**：它只保证「露出来」、不保证落在哪，
      而且会同时动多个容器，平台那条 sticky 顶栏就把标题盖住了。
      正确做法是「逐层补偿」——沿锚点的**可滚祖先链**（只算
      `overflow: auto/scroll/overlay` 且内容高于可视区的容器）逐层调 `scrollTop`，
      不足的位移交给上一层、最后一层给 `window`，来回几趟收敛。
      只沿祖先链走，链外的滚动区（侧栏菜单、直播互动栏评论列表）一定不碰
      —— 与「上滑到顶 / 下滑到底」的口径一致。
    - **异步动作的「失败」不能当场判**：点下切换后 React 要重渲染、要拉接口，
      目标状态不会立刻翻。所以必须配冷却（2.5 秒级），且「点满次数」只**停手**、
      不判失败；真正的失败结论留给**收尾复核**（重试表跑完先再看一次状态，
      已达成就算成功）。
    配套：滚动的重试表要比切页的**靠后得多**（切页那一刻目标区块通常还没挂载），
    命中即停；全部试完仍没找到锚点时，往控制台打一条诊断并**列出页面上像标题的短文本**
    —— 这是把「判据写错了」和「页面还没渲染」分开的唯一线索。
50. **给平台页面注入「取代型」控件，挂载点必须脱离平台的组件树。**
    （2026-10-20 定，来自小黄车自动刷新那次）
    症状很好认：控件在页面上**周期性闪一下**（消失又出现，间隔等于功能自己的刷新周期）。
    成因：平台是 React，只要它重渲染那个区块，就会按自己的虚拟树重建子节点 ——
    **我们插进去的外来子节点会被一并清掉**。凡是「我们每 N 秒点一次平台按钮」的功能，
    都必然触发这轮重渲染 ⇒ 挂在平台容器里的控件活不过一个周期。

    正确做法：控件挂 `document.body` + `position:fixed`，坐标每轮从目标元素
    的 `getBoundingClientRect()` 现取（视口坐标，不做任何容器换算）。
    - 好处：平台怎么重渲染都碰不到我们；少了 padding box / `clientLeft` /
      `scrollTop` 这一整类「绝对定位才有的」换算坑。
    - 代价：fixed 不跟页内滚动 ⇒ 必须**每拍重量坐标**，且目标滚出视口时
      把自己 `display:none`（否则会停在屏幕某处盖住别的内容）。
      250ms 一拍的重量开销可忽略（只读一个矩形）。

    **★ 别把它做成「取代型控件」**（2026-10-20 追加，用户否掉了最初那版）：
    最初的做法是「把平台那枚按钮设成 `opacity:0`，再用自己的按钮盖住它」。
    用户原话：「不做整合按钮，做在这个原生刷新按钮的左边…用颜色区分，
    不要有一直旋转的圈圈，很影响我的注意力」。教训三条：
    - 「取代」要多维护三件事（藏起来 / 每拍补一次透明 / 还原时写回原值），
      而**收益只是省了一个按钮的位置** —— 平台自己的按钮本来就该留在那儿。
      真要「加东西」，**加在旁边**（左侧一盏灯）比盖在上面便宜得多：
      原生控件一个像素都不动，我们只负责「贴上去 + 跟住它」。
    - 状态提示优先用**静态颜色**；动效要克制 —— 旋转会被余光持续牵走，
      呼吸（3.6 秒一轮、只呼吸外圈光晕）才是「安静地告诉你它还活着」。
      **呼吸只做在外圈光晕上、灯珠本体恒定满色**：灯珠整体变淡会让颜色「糊」掉
      （绿在 alpha 0.75 时对比度只剩 2.55，达不到 3:1）。
    - **点一次只发一套事件**：`pointerdown → mousedown → pointerup → mouseup → click`
      各一次。**不能既调 `btn.click()` 又补全套** —— 那等于平台收到两次点击
      （每 N 秒刷两遍，正好是这个功能最怕的事）；只发 `click` 也不行 ——
      平台有时在捕获阶段 `stopPropagation` 把它吞掉。

52. **「这个功能反应慢」，八成不是某一处慢，而是延迟被几步串起来叠高了。**
    （2026-10-20 定，来自用户一句「我觉得检测下滑比较久」）
    - **现象**：切页不到 1 秒就好了，但下滑要等 4~5 秒才动 —— 用户体感是「卡」。
    - **查法：把这条链路每一步的耗时写成一张表，别猜。** 本次摊开是这样：
      `800ms 首轮 → 1600ms 那次因冷却被跳过 → 2800ms 点第 2 次卡片 → 4500ms 才
      开始铺滚动表 → 5100ms 滚动第 1 次 → 锚点没挂载就再等到 5.7/6.7/8.0 秒`。
      五步各自都「不算慢」，叠起来就是 5 秒。**看到「慢」先做这一步，再动手改。**
    - **三个典型叠法**（本次全中，逐个拆）：
      1. **把「做下一件事」的触发条件挂在「做够 N 次上一件事」之后。**
         卡片要点满 2 次才 `scheduleScroll()`，而两次点击之间隔着冷却 ——
         真正卡住的不是滚动，是这个「点满 2 次」的前置条件。
         推论：**两件可以并行的事，别串成前后置关系**。点下去就可以开始找目标。
      2. **重试表只考虑了「最慢情况」。** 起步 600ms 是照「接口要几秒」定的，
         可实际锚点常常在 120ms 内就挂载好了。**重试表要前密后疏**：
         前 1 秒铺 4 档抓快的，尾部拖长了兜慢的 —— 单向「均匀稀疏」两头都亏。
      3. **只在闹钟点上看一眼。** 锚点出现在两次闹钟之间，就得白等一整个间隔，
         而间隔越往后越大（尾部 2 秒级）。**加 DOM 观察器做唤醒**：
         新节点文本里带目标词就叫醒一次扫描，把「等到下一个闹钟」这段直接抹掉。
    - **DOM 唤醒的三个必须**（否则会从「慢」变成「卡」）：
      ① **必须节流**（200ms 级）：React 渲染一屏会连开几百个 mutation 回调，
         每个都扫全文档就是白烧 CPU；
      ② **回调里只读新增节点自己的文本**，不含目标词直接放过 ——
         绝大多数渲染（数字跳动、行内更新）过不了这关，等于零开销；
      ③ **到位 / 放弃 / 用户接管时都要 `disconnect()`**，否则留下一个空转的
         observer。**统一把 disconnect 收进 `clearScrollTimers()`**，
         所有「不让继续了」的路径都从那里出去，比在每个分支各写一遍可靠。
    - **顺带一条措辞纪律**：为了提速而把「等确认」提前成「先动手」时，
      提示语必须跟着降级 —— 卡片档读不到选中态，就只能说「已点」不能说「已切到」。
      **提速不能连带把「猜测」说成「事实」。**

53. **「它会自己停」类功能：判「能不能干活」的判据里，别混进「看不看得见」。**
    （2026-10-20 定，来自小黄车自动刷新：用户报「滚到页面下方看商品时会停，
    即使没开播也会停」）
    - **现象**：自动化跑得好好的，用户往页面下方滚一会儿再回来一看 —— 灯是灰的，
      刷新也不跑了，只能刷新页面。
    - **根因不是「超时太短」，是「不该算失败的事被算成了失败」**。当时的判定链是：
      「取目标按钮矩形的五个点 → `elementFromPoint` 看有没有被浮层挡住」。
      按钮滚出视口后，**这五个点全在视口外**，代码逐个 `continue` 跳过 ⇒ 命中数 0
      ⇒ 判「点不着」⇒ 连败 3 次 ⇒ 停机。
      ⚠️ **推论：先别急着调大超时 / 放宽次数。** 只要「误判」还在，
      把 30 秒延到 5 分钟也只是「5 分钟后照样停」。
    - **正确切分**：「能不能程序化点到它」与「它看不看得见」是**两件不相干的事**。
      - 能否点到 = 节点还在文档 + **有真实尺寸**（不是 0×0）+ 没禁用 / 不在加载中。
        **不含视口条件。**
      - 「五点采样」这类**模拟人手**的判据，只在目标**本来就在视口里**时才跑 ——
        那时它才有意义（防被浮层盖住）；视口外跑必然假阴性。
      - 而「看不看得见」只用来决定**浮层控件的显隐**，绝不用来决定「功能要不要停」。
    - **真故障也别做成单向停机。** 连败到上限时，改成「慢速重试」（30 秒轻试一次），
      条件一恢复就自动回到正常节奏并报一声「已恢复」。
      **停机是单向的**（用户只能刷新页面，而且常常没注意到它停了）；
      **慢速重试是双向的**（它一直在等）。代价只是故障期间每 30 秒空点一次。
    - **「判不出」要连续确认，别一次就停。** 判定每 2 秒跑一次，页面正在重渲染
      （尤其我们自己刚点完刷新）时单次判不出是常态。要求**连续 3 次**都判不出
      才转「未知」，期间保持上一次的结论继续刷 —— 否则用户会觉得「莫名其妙就停了」。

54. **「让闸门变绿」的手段里，白名单是最贵的一种 —— 它会把拦截那一行永久压死。**
    （2026-11-02 定，来自「自测总是红」的排查）

      - 闸门启动时做**两表冲突检查**（`validate_tables`）：同一个词既在拦截表又在白名单
        ⇒ 直接报错中止，逐条打印两边理由，要求二选一。
      - 真要放行 ⇒ 从拦截表**删词**并写清为什么不再拦；不要用白名单去压。
    - **推论（适用于所有闸门，不只这一道）**：
      一道闸门开始「常态报红」时，先怀疑**闸门自己的判据**，再怀疑被测代码。
      用白名单 / 跳过 / 放宽阈值去消红，等于把这道检查永久关掉 ——
      它不会再提醒你任何事，而你仍然以为自己有这道检查。
