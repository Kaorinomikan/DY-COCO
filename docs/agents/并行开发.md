## 八、多会话并行开发（2026-10-11 落地，改代码前必读）

### 为什么有这一章

本工程曾经出现过**两个会话同时在同一个目录改代码**——2026-10-11 实测撞到，
两个会话改的是同一批文件（`manifest.json` / `popup.js` / `nav.js`），
互相覆盖、还互相以为是自己写的。后来排查并发风险时发现，
根源是**缺少隔离**：会话之间只靠"自觉不碰对方的文件"，而这条自觉无法验证。

现在改成**物理隔离** + **机械闸门**：每个任务一份独立目录（git worktree），
写入天然不冲突；回收由脚本统一把关。

### ★ 用户用中文对话,助手负责执行(2026-10-11 用户明确要求)

用户原话:「我用纯中文对话,你帮我执行操作,比如开新的任务分支开发,
**后台是英文无所谓**。」

→ **不要让用户碰命令行。** 用户只说中文口令,助手跑脚本,汇报时全中文。
详见记忆文件 `DY-COCO-并行开发口令.md`。

**中文口令表(收到就直接执行,不必再向用户确认)**

> 2026-10-11 用户定:**流程从简,顺序固定** —— 「回收 / 合并 / 验收」是**同一个口令**,
> 执行顺序:**先自检(合并前)→ 合并进主干 → 自动清理工作树副本**。一步完成。

| 用户说 | 助手执行 |
|---|---|
| 「开一个任务叫 X」/「开工 X」 | `bash scripts/开工.sh X "描述"` |
| 「继续开发 X」/「继续 X」 | 汇总 X 的进度接着做(`bash scripts/继续.sh X` 起步) |
| 「回收 X」/「合并 X」/「验收 X」 | `bash scripts/回收.sh X`(**自检→合并→自动清理副本**) |
| 「只看 X 能不能合」 | `bash scripts/回收.sh X 只看`(仅预检) |
| 「给 X 写派活说明」 | `bash scripts/说明.sh X` |
| 「看看任务」/「看板」/「开发计划」 | `bash scripts/看板.sh`(2026-10-11 用户定:问「开发计划」一律直接给看板表格,不翻文档) |
| 「攒够几个点了」/「够推了吗」 | `bash scripts/计点.sh`(**唯一事实来源**,门槛 5;功能点逐项计 + 文档/脚本类合并计 1 点) |
| 「推送」 | 走完整推送期流程(见「六、发布流程」);成功后「待推送」栏由脚本自动重置 |

中文脚本只是薄封装,底层行为与下面的 `wt-*.sh` 完全一致。
**任何时候都别把英文命令甩给用户**,自己跑、自己读输出、用中文汇报。

> **2026-10-11 用户定(铁律):「合并 / 回收」口令只作用于本会话自己开的任务。**
> 看板上别的会话开的任务一律**不碰**——不预检、不合并、不清理、不代劳,
> 哪怕它显示空任务、零提交、或看起来已完成。收到「合并」口令时,只回收
> 本会话自己开且用户点名的分支;不是自己的任务就明确告知用户不归本会话管。
### 三个底层脚本(中文入口最终调用它们;全部只做本地 git 操作)

```bash
# 开一个新任务 —— 建独立工作树 + 分支 + 写任务卡
bash scripts/wt-new.sh <名字> "任务描述"      # 名字支持中文,实测可用

# 看所有任务进展
bash scripts/wt-list.sh

# 回收一个任务(默认只预检,不做任何改动)
bash scripts/wt-merge.sh <名字>                  # 预检:能合吗?会不会冲突?
bash scripts/wt-merge.sh <名字> --go             # 真合并到本地 main(仍然不推送)
bash scripts/wt-merge.sh <名字> --go --cleanup   # 合并后删掉工作树与分支
```

工作树落在 `C:/Develop project/DY-COCO-wt/<名字>/`——**故意放在工程目录之外**:
工作树目录本身是一份完整的扩展副本,若落在可写范围内容易被误当成"工程本体"。

**任务名可以用中文**(2026-10-11 实测:分支 `task/回到顶部`、
目录 `DY-COCO-wt/回到顶部`、git 操作全部正常)。仓库已设 `core.quotepath=false`,
否则 git 会把中文文件名显示成八进制转义、完全不可读。
仍需避开:空格 `/ \ : ? * < > | ~ ^ %`,不能以点开头,不能是 HEAD/main/master。

✅ **开任务不再要求主工作区干净（2026-10-13 改）** —— 旧版把它当**硬闸门**，
理由是「怕把半成品带进新分支的基线」。**这个理由不成立**：
`git worktree add -b <分支> <目录> main` 是从 **main 的提交对象**检出内容，
主工作区里未提交的改动根本不会被带过去。

旧闸门的实际后果是：任何一个会话动过主工作区（改文档、调脚本、甚至只是
留下一个临时文件），**所有会话就都开不了新任务** —— 主干被占用即全线停摆。
现在 `wt-new.sh` 改成**只提示、不拦**。要记住的只有一条：
**别顺手把别人的改动 `git add` 进来**。

### 文件归属：什么是自己的，什么是共享的

**自己的文件（随便改，零冲突）**
- 你新建的任何 `src/**` 文件
- 你的工作树里的 `TASK.md`（本地忽略，不入库）

**共享文件（只允许「末尾追加」，绝不插到中间）**

| 文件 | 追加什么 | 追加到哪里 |
|---|---|---|
| `src/content/flags.js` | 你的开关元数据对象 | `DYC_FLAGS_META` 数组**末尾** |
| `manifest.json` | 你的脚本路径 | 对应 `content_scripts[].js` 数组**末尾** |

> ⚠️ 「末尾追加」不是可选项。实测：两个任务都在同一个锚点（如第一个 `debug` 项）
> 之前插入，git **无法**自动合并，必然冲突。插到数组末尾也一样会冲突——
> 所以规则是"由回收脚本统一追加"，见下一节。

### 四条不可违背的红线（违反即回收被拦）

1. **不准改 `manifest.json` 的 `version` 字段** —— 版本号只在推送期由 main 统一改
2. **不准在任务分支上 `git push`** —— 推送是 `publish.sh` 的职责，由用户决定时机
3. **不准打 `git tag`** —— 标签只在推送期由 main 打
4. **不准改 `update-manifest.json`** —— 它是派生文件（当前 25 个文件的 sha256），
   任务分支各自生成必然全文件冲突。**只在 main 上、只在推送期生成一次**
5. **不准在任务分支上写三份文档的"本版新增"** —— README / AGENTS.md / 开发日志.md
   由回收方在 main 上统一写，任务分支里一律不碰

这五条已写进 `wt-merge.sh` 的机械闸门，**不需要靠自觉**：违反会在预检阶段被拦下。

### 共享文件冲突怎么解（重要，且有陷阱）

两个任务都往 `DYC_FLAGS_META` 加一项时必然冲突。`wt-merge.sh --go` 会自动调用
`scripts/resolve-array-merge.py` 做**三方语义合并**（回到 base/ours/theirs，
按数组元素重组，每个元素从原文件整段抠出）。

**⚠️ 千万别用 `git merge-file --union`**，实测会**静默损坏**文件：
git 会把双方共有的尾部（`default` / `pages` / 收尾的 `},`）当成公共部分挪到冲突块外，
union 于是把冲突块内两侧的前半段堆在一起——两个对象字段揉成一个：
```js
{ key: 'backToTop', ..., key: 'skuSearch', ... }   // 语法合法但 backToTop 丢了字段
```
`node --check` 会放行它，只有运行时才炸。**比报错危险得多。**

脚本也会在下列情况主动报错、交人工，绝不猜：
- 两个任务新增了**同名** key
- 同一个元素被两边同时改动且内容不同
- 结果语法检查不过

### 真机冒烟是合并硬前提（2026-11-04）

改过 `src/**` 或 `manifest.json` 的任务，合并命令必须显式带当次确认：

```bash
DYC_SMOKE_OK=1 bash scripts/回收.sh <名字>
```

冒烟至少覆盖主路径、一个异常路径、控制台无新增错误。脚本只能强制“确认存在”，
不能证明平台行为正确；没做过就不要声明。纯脚本/文档任务不需要该变量，
`wt-merge.sh` 会按分支改动范围自动判断。

### 回收流程（归总由一个人做）

```
各任务分支写完 → wt-merge.sh <名字> --go --cleanup(回收.sh 已封装)
  → ① 合并**前**自检:分支改动全部提交 / `check-syntax.py --changed` /
     真机冒烟声明（改过 `src/**` 或 `manifest.json` 时必需）/
     未碰版本号标签 / 与 main 冲突预判(共享数组文件可自动解)
  → ①.3 按改动自动跑 manifest 顺序、产品文案、性能闸与断言体检（提示不阻断）
  → ①.5 合并**前**在任务工作树内跑 `run-selftests.py --changed`:
     只跑与本任务改动相关的用例,红了就地修。
     为什么在合并前:合并后才发现红 = 重开工作树 → 再改 → 再回收一整轮。
     跳过用 `--no-selftest`(仅在明确知道自己在做什么时)。
  → ② 全部通过才真正合并
  → ③ 成功后同步桌面 COCO TEST 并**逐文件 sha256 自证一致**(失败会明确报错)
  → ④ 自动删工作树与分支
→ 全部回收完 → `bash scripts/计点.sh` 看够不够 5 点(功能点 + 最多 1 个基建点;不够就不推,继续攒)
              → 够:在 main 上统一：改版本号、重生成 update-manifest.json、
              写三份文档 → publish.sh --dry-run（含全量自测）→ publish.sh
              (同一受测内容复用全量通过凭据；内容变化自动重跑。
               publish.sh 推送成功后:同步 + 校验 COCO TEST、并把「待推送」栏重置,
               该重置改动记得补一次本地提交)
```

**自检永远在合并之前**(2026-10-11 用户定)——不合格的代码拦在主干之外;
合并成功后副本自动清理,不再有单独的「清理」步骤(`清理.sh` 仅作手动兜底)。

**主工作区脏不再阻塞回收(2026-10-13 改)**：旧逻辑是「主工作区只要脏就拦」，
结果是别的会话一改文档，本会话就回收不了。现在只在**未提交改动与本次合并
涉及的文件有重叠**时才拦（那才是 `git merge` 真会报错的场景）；
不重叠时打一行提示照常回收。

**排查「回收到底稳不稳」的两条命令**（随时可用）：

```bash
bash scripts/看板.sh                              # 各任务领先/落后/能否回收(含待推送计点)
bash scripts/sync-coco-test.sh --check            # 桌面测试档是否等于源码
bash scripts/sync-coco-test.sh --from <工作树名>   # 把未合并的工作树镜像进测试档(真机验证)
bash scripts/sync-coco-test.sh --status           # 测试档现在装的是主干还是某个工作树
bash scripts/计点.sh                              # 本次攒批到底算几个有效功能点(门槛 5)
```

**绝对不要让任务分支各自发布**——版本号、自更新清单、扩展加载目录全绑在 main 上。

### 任务状态必须实时查询,禁止复用快照(2026-10-11 实测教训)

其他会话随时可能回收任务 / 开新任务,本会话**收不到任何通知**。
实测:本会话 14:00 出的任务快照里「手型描边」还在,14:06 被另一会话回收合并,
14:08 本会话仍按旧快照把它报成「进行中」,被用户指出。

硬性规矩:

- **凡回答涉及任务 / 分支 / 工作区状态,必须当场重跑 `bash scripts/看板.sh`**,
  禁止拿上一次的输出当现状 —— 哪怕几分钟前刚看过。
- 若实时结果与上次快照**有出入**(任务消失、新提交、分支增减、版本号变化),
  **第一句话先报**「自上次汇报后外部发生了变化:…」,再回答用户的问题。
- 涉及某任务的具体进度时,连 `TASK.md` 的进度续写段一起重读,不凭印象。

### 自测断言怎么写才不「总是红」（2026-11-02 用户要求，现行）

> 用户原话：「自检自测总是红，你修复一下，降低自测出现红的概率，
> 节省我每次做完新功能等待时间。」

现状盘点（2026-11-02 实测）：44 个自测、2283 条断言，其中 **420 条是源码文本断言**
（对 `readFileSync` 的内容做正则匹配），**124 条还绑死了中文文案**。
红的主因不是功能坏了，而是断言写死了**实现细节**：改一句文案、多一个空格、
换个声明方式、插一行注释，断言就红。

**四条硬规矩（新增/修改断言时必须遵守）**：

1. **不绑死自己写的文案** —— 不要写 `/var SOURCE = '自动循环讲解';/`。
   改成 `/var SOURCE = '[^']+';/`（只要「有来源词」），或断言行为而非字面。
   平台原文（`'讲解'`、`'开始活动'` 这类要匹配页面按钮的）**例外**，必须原样保留。
2. **不绑死空格与排版** —— 正则里用 `\s*`，别用字面空格：
   `/var TICK_MS = 2000;/` → `/var\s+TICK_MS\s*=\s*2000\s*;/`。
3. **不绑死行号与定长切片** —— 别用「第 12 行」「`slice(i, i+80)`」。
   先 `indexOf` 锚点再取窗口（窗口 ≥700 字符）。
4. **断言失败先判断「是断言过时还是功能坏了」，再动手** ——
   判断依据看 `run-selftests.py` 的归因输出。确属断言过时，按新写法更新；
   若是功能真坏了，修功能。**⛔ 绝不为了让自测变绿而删断言或放宽语义**
   （2026-11-01 教训：正则被改宽 ⇒ 真机匹配不到 ⇒ 静默失效，自测还是绿的）。

**体检器**（改过自测文件后跑一次，只提示不阻断）：

```bash
"…/python.exe" scripts/selfcheck-assertions.py --changed
```

它按「文案绑死 / 空格绑死 / 行号绑死 / 定长切片」四类指出具体行号与建议写法。
看到提示**不是**让你删断言，而是换成等价但不绑死实现细节的写法。

### 新增功能的标准步骤（写在模板里了）

`scripts/feature-template.js` 是**新功能模板**，含完整注释：
1. 把它复制到 `src/live/<你的功能>.js`
2. 改 `id` / `flag`
3. 到 `flags.js` 的 `DYC_FLAGS_META` **末尾追加**开关元数据
4. 到 `manifest.json` 对应 `js` 数组**末尾追加**脚本路径
5. 中间态跑 `check-syntax.py --changed`；口径定稿后回收自动跑 manifest 顺序 / 文案 / 性能 / 相关自测
   > 2026-11-02 核实：旧文档这里写的 `verify-flags-arch.js` / `verify-toolbar-arch.js`
   > **在仓库里并不存在**（早已移除），照旧文档敲会得到「找不到文件」。
   > 别把它当成「闸门失败」去排查，那是文档漂移。

> 模板故意放在 `scripts/` 而非 `src/live/`：既不会被浏览器执行，
> 也不在自更新清单的扫描范围（`DIRS=["icons","src"]`），商家更新时收不到它。

### 工具栏 ctx 的真实接口（只有三个，别自己假设）

`dycRegisterTool({ id, flag, label, render(ctx), onEnable() })` 中：

| 成员 | 说明 |
|---|---|
| `ctx.makeButton(文字, 回调)` | 统一样式的按钮 |
| `ctx.report(对象, 类型, { count })` | 统一状态栏；来源默认取注册项 `source / label / id`，也可显式传入 `source`；结果放 `count` |
| `ctx.bar` | 工具栏容器节点，需要复杂布局时才用 |

`ctx` 上**没有** `el` / `setText` / `onClick` / `setStatus`——需要就用原生
`document.createElement`，样式类名 `.dyc-tool` / `.dyc-tool-btn`。
