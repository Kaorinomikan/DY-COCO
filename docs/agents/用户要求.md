## 1. 推送节奏：自动合并、手工推送

- 推送前由助手自己审核（通读改动、跑机械闸门、确认功能自洽），用户不是验收入口。
- **合并自动、推送手工**（2026-11-05 用户定）：任务工作树闸门全过即回收合并，
  不等口令；**推送必须等用户明确下令**，助手只能报进度、不能自己推。
  5 点攒批门槛降级为提示口径（唯一事实来源仍是 `scripts/计点.sh`；
  看板、发布闸门都问它，别处不许写死数字）。
- **计点口径**：
  - **功能点**（逐项计，不设上限）：必须同时满足「落在扩展本体」
    （`manifest.json` / `icons/` / `src/` / `update-manifest.json` / `install/`）
    与「用户可感知」（新增功能、可观察的行为改进、用户能遇上的 bug 修复）。
    内部重构、措辞调整、无害清理不算点。
  - **基建点**（合并最多 1 点）：文档、脚本、流程、定时任务等非扩展本体改动，
    无论多少条只算 1 点。目的：让「本地有改动但没推送」在看板上永远看得见。
  - **同一处反复修只算 1 点**；别处新出现的问题才算新点。
  - **同一「未上线」功能点上限恒为 1 点**：攒批期间无论迭代几轮都合并为
    一条 `### ` 条目；已上线后的重做/改版同样合并计 1 点。
  - 记账位置：`开发待办.md` 「待推送」栏，一条 = 一个 `### ` 标题行；
    非本体条目加 `[文档]`/`[流程]`/`[基建]`/`[脚本]` 标记归入基建点；
    无意义小改动加 `[不计点]` 并注明理由。
- **「5 个」按增量算**：只数相对在线版新增的点（功能点逐项 + 基建点最多 1）。
  没到 5 点就继续攒；攒批期间本地正常提交，不打标签、不推送。
- **推送成功后必须重置计数**：`publish.sh` 自动调 `scripts/reset-pending.py`
  清空「待推送」栏；该重置造成的改动由助手补一次本地提交。
- **机械闸门**：`publish.sh` 攒批门槛直接问 `计点.sh`；**用户主动下令推送
  即视为强制推**，用 `FORCE_PUSH=1 bash publish.sh` 执行，不再反问、
  不再因未达 5 点中止。没有用户口令时任何通道都不得推送。
- **有开发中任务时禁止推送**：只要存在未合并的并行任务分支/工作树，或会话
  正在进行尚未提交的功能改动，就禁推（哪怕已够 5 点），最多向用户报明攒批
  内容与阻塞原因等裁决。开发中任务全清零、闸门全过只代表「可以推」，
  仍须用户下令。
  - 推送动作前最后一刻必须重新查 `git worktree list` 与
    `git branch --list 'task/*'`，不沿用合并时的旧判定；
  - 该规矩已落成 `publish.sh` 机械闸门（检测并行工作树 / task/* 残留分支，
    `--dry-run` 同样生效）。
- **门槛提示时机**：只在「合并分支（回收任务）」且该次合并使开发中任务全清零
  时数一次点，报一句「已攒 N/5 点，等你下令推送」；平时一律不检测。
  未达 5 点用户也可下令推送（他说推就是推），点数只作进度参考。
- 版本号按第 3 条：以在线版为基准 +1，不跳号、不占号。
- 推送内容 = 主干 + 标签（不建发行版、不传附件，见第 8 条）。
- 不得把与本次改动无关的东西顺手推上去。
- 推送完成后主动告知用户本版包含哪几个特性。
- **「查在线版、对版本号」只在推送时做一次**；开发期一律纯本地（两阶段划分
  见主文件「开发流程」）。

## 2. 推送前必须写详细的版本对比说明

推送时对比上一个版本，详细写出：新增了什么功能、改进了什么、修复了什么问题、
有无破坏性变更。不能只写「修复若干问题」这类概括。

## 3. 版本号用年月日格式，不要随意刷新

- 格式：**`YY.MM.DD.N`**（如 `26.10.10.1`）：年(两位).月.日.当天第几版。
- 同一天多次改动只递增最后一段；到新日期则日期刷新、序号归 1。
- 严禁随意刷新版本号，只有实际产生可发布的变更时才动。
- **推送时的版本号必须是在线版的下一号**，不跳号、不为未推送的改动反复占号。
  日期段仍跟随真实日期（不是「最后一段 +1、日期永不刷新」）。
- 对照口径由 `publish.sh` 打印；离线时以本地最新标签兜底（`next-version.sh --offline`）。
- 该格式满足 Chrome 对 manifest `version` 的要求（1~4 段点分整数、每段 0~65535），
  直接写进 `version` 即可；发布标签 `vX.Y.Z.N` 与 manifest 完全一致。

## 4. 禁止强制推送

- 用 `git push`，不加 `--force`；脚本里一律普通 push。
- 推送冲突/非快进时先报告用户，不自行强推。

## 5. 推送前必须先检查并更新说明文档

硬性顺序：先读 `README.md`、`开发日志.md` 对照本次改动 → 做出全面对应修改
（新功能补功能清单与操作路径、行为变更改 FAQ、参数变更改示例）→ 自审一遍
确认文档与代码一致 → 确认无问题后才推送。不允许「代码改了、文档还是旧的」。

## 6. 工程内必须留存开发日志与组件描述

- `开发日志.md` 必须留在工程目录内（`C:\Develop project\DY-COCO\`），
  WorkBuddy 工作区另存一份副本，两边都要维护。
- **组件描述由 `AGENTS.md`（索引）+ `docs/agents/组件职责.md`（全文）共同承载**，
  用途是跨模型交接：新模型先读主文件，再按索引深入对应子文档即可上手。
- 写文档时假设读者是完全不了解本项目的新模型或新人：每个文件干什么、
  数据怎么流动、哪些地方看起来奇怪但是故意的（附原因）。

## 7. 用户口头说「记下来」的偏好，要写进文档

不只记在对话或记忆文件里，要落到工程文档中（按第 0 条准入闸决定落在哪个文件），
让后续接手的模型也能看到并遵守。

## 8. 禁止创建 Gitee 发行版

- **「推送」= `git push` 主干 + 推标签**，就这两件事。
- **永不创建 Release、永不传 zip 附件**，不再生成面向商家的分发包；
  任何理由（含「重建更省事」）都不得跳过。
- 日常推送只用 `publish.sh`（终点 = 主干与标签都已推送且指向同一提交）。
- `scripts/gitee-release.py` 保留但加硬闸门：默认模式直接拒绝执行，
  必须 `DYC_ALLOW_RELEASE=1` 才放行；只读模式（`--dry-run` 等）不受限。
- 为什么可以不要发行版：自更新链路检测走 `tags.atom`、下载走 `raw/<标签>/`，
  完全不碰发行版；且 Gitee 会清理旧发行版，维护它只会让商家链接失效。
- 例外备忘（不影响本条）：v26.10.14.2 曾破例建过一次发行版，仅此一次；
  若仓库里出现它之外的发行版才是异常。

## 9. 每个功能都要带开关，默认值按统一口径

- 每个新功能都要有独立开关，用户能在弹窗里自行关掉，不需要改代码。
- 默认值：调试类开关默认**关**，其余一律默认**开**。
- 存储：统一放在 `chrome.storage.local` 的 `dybFeatures` 对象里；
  **缺省即默认值**，不写迁移代码、不把「键不存在」当关闭信号。
- 即时生效：内容脚本订阅 `chrome.storage.onChanged`，拨动后已打开页面立刻响应；
  不另搭 popup → content 消息通道。
- 新增开关的完整步骤见 `docs/agents/组件职责.md` 的 `flags.js` 说明。

## 10. 只改工程目录，不许碰浏览器里跑着的扩展

- **可写范围只有 `C:\Develop project`**（本项目即 `DY-COCO` 子目录）；
  工程目录之外一律只读，能不读也不读。
- 绝对不动：浏览器侧扩展安装目录（`C:\DY-COCO`、各浏览器
  `Default\UnpackedExtensions\…`、`Service Worker\ScriptCache` 等）、
  注册表 / FSA 授权记录 / IndexedDB 扩展元数据；不用自动化点「重新加载/更新扩展」。
- 验证不是 AI 的活：用户自己点「检查更新/安装更新」走真实自更新链路核对；
  不代劳、不催、不问「验收了吗」。
- 改动抵达浏览器的唯一出口 = 推送（主干 + 标签）→ 用户侧自更新拉取；
  不允许直接往扩展目录拷文件。
- 需要知道「浏览器里跑的是什么版本」时，只问用户、只让用户去看。

## 11. 请用户验收前必须先概述「要验收什么」

- 每次请用户验收前，用几句话说清三件事：验哪个（版本号 + 哪几个功能）、

  验完会怎样（通过后推什么）。
- 必须短：3~5 条要点以内，不贴代码、不复制 AGENTS.md 原文、不倒无关历史。
- 不许只丢「请你验收」四个字。
- 手上有未验收项时主动列出，别等用户问。
- 现行顺序：**先自审并推 → 再告知用户验收**（推送完成后附这段概述），
  不再有「等用户验收才推」这一步。

## 12. 推送完成后必须逐条列出「本轮更新点」供用户测试

- 推送成功后立刻做，不等用户问：单独给出「本轮更新点」清单，
  按新增/改进/修复分类，逐条写明用户能观察到什么变化。
- 每条要能让用户立刻去测：哪个页面、点哪里/看哪里、预期现象。
- 指出本轮与上一批的区别，上次测过的不重复列。
- 清单末尾附对比口径：本轮版本号 vs 在线旧版本号，以及装完更新后弹窗
  应显示的版本号。
- **推送汇报必须同时附重跑后的最新看板**（`scripts/看板.sh`，
  按分类独立表格形态）。

## 13. 所有新功能一律走并行开发，用户忘说「开工」也要主动开

- 凡新增用户可见功能或功能级改动，一律先
  `bash scripts/开工.sh <名字> "<一句话描述>"` 开独立工作树 + 任务分支，
  在 `DY-COCO-wt/<名字>/` 里做，**禁止直接在主工作区改功能代码**。
- 用户没说「开工」也不例外，助手必须主动走流程，并用一句话告知开了什么任务。
- bug 修复同样走并行开发（评审免、分支不免）。
- **普适判据**：凡要写工程目录里的任何文件（代码/清单/文档/脚本），默认开分支；
  只有确定不落盘或只读操作才在主工作区直接做。
- 主工作区只允许非功能性改动：并行机制/脚本本身、发布流程、文档同步、更新清单等。
- 完成后走 `回收.sh`，再由主工作区统一攒批推送。
- 理由：隔离 —— 两个会话改同一文件会互相覆盖，事后分不清是谁改的。

## 14. 发布前必须做性能常规检查，损耗过大就暂停并告知用户

- 检查固定在两个机械节点：`wt-merge.sh` 合并前与 `publish.sh` 发布前各跑一次
  `python scripts/perf-check.py --gate`；不再靠人记得手跑。
- 查什么：会不会导致商家页面卡顿/假死的反模式，静态扫描 `src/**/*.js`。
  【拦】= 高频定时器(<200ms)/同步网络请求/同步自旋忙等，命中即暂停发布；
  【提示】= 循环内读布局、循环内逐个插节点等，只提示不阻断。
- 被拦后必须逐条转述给用户（文件:行号 → 为什么会卡 → 优化方案），
  不得只说「没过」。
- 白名单是例外通道不是逃生门：确属已论证过的良好模式才登记进
  `scripts/perf-check.py` 的 `WHITELIST` 且必须写理由，每条豁免都会列数。
- 如实说明能力边界：静态扫描查确定性反模式，测不出真实毫秒数；
  真实手感由用户真机验收观察。

## 15. 独立按钮/控件不随页面缩放改变自身大小（默认开发规则）

- 扩展注入的一切独立控件（悬浮球、搜索框、面板、弹层、按钮组等），
  无论页面怎么缩放（浏览器缩放、`zoom`、`transform: scale`、rem/em 变化），
  控件自身尺寸必须稳定。
- 尺寸一律用固定 `px`，禁止用 `em`/`rem`/`%` 描述控件自身宽高、字号、
  内边距、边框（`%` 仅允许用于撑满父容器的布局意图）。
- 样式与页面隔离：Shadow DOM（`mode:'closed'`）或根节点 `all: initial` 后
  再写自己的样式，防页面全局 CSS 渗透。
- 抵抗页面级 `transform: scale`：宿主被波及时可读实际缩放比反向抵消
  （仅在有明确问题场景时做，不预防性过度设计）。
- 既有控件逐项自查：下次改到该文件时顺手把非 px 的自身尺寸改为 px，不单开任务。
- 例外（只此两处）：中控台「回到顶部 + 搜索按钮」两枚浮动按钮跟随页面缩放
  （已删除其 BASE_DPR zoom 补偿）；其余注入控件维持不变。
- 本条是默认开发规则，违反的代码在自审时视为不合格。

## 16. 消息提示栏（dialog.js 状态条）全组件统一

- 左下角状态条（`setStatus`/`toast`/`updateProgress`/`finishStatus`/`failStatus`）
  是全局共用组件；改它的结构/动画/生命周期/配色时，所有调用方
  （search.js / toolbar.js / nav.js / clear-stock.js / inject-button.js 等）
  必须同步核对更新。
- 调用方禁止自建样式，一律走 setStatus 家族接口；确需新类型时改
  dialog.js + `msgbox.css` 统一加。
- 生命周期以 dialog.js 为准：所有消息统一 3 秒掉落，running/富状态原地合并续期；
  调用方不得用 timeout 参数恢复「常驻」。
- **收录规则**：消息盒子只收录「结果」与「异常」——success/error/alert 收录；
  info（操作回声）、warning（前置提醒）、running（过程进度）一律不收录。
  个别例外用 `keepHistory` 显式覆盖。
- **同一件事反复发生 ⇒ 用 `histKey` 只占一格**：给 `setStatus`/`toast`/`failStatus`
  传 `histKey:'固定键'`，同键消息就地刷新不流水增长。走 `histKey` 时合并分支
  也会回写历史（区别于普通消息）。
- **改核心必跑全量核验**：动 dialog.js / `msgbox.css` / style.css 后，自测覆盖
  所有调用方的消息路径（至少 search + clear-stock）。入库自测：
  `scripts/自测-消息盒子持久化.js`、`scripts/自测-后台状态.js`，
  统一入口 `scripts/run-selftests.py`。
- 本条是默认开发规则，与第 15 条同级；文案结构见第 21 条。

## 17. 新功能一律先出评审方案，方案定稿后才开工

- 凡新增用户可见功能或功能级改动，接需求后第一步是出方案评审稿：
  目标、涉及文件、改动思路、关键交互/界面行为、已知风险与取舍，中文给用户过目。
- 之后多轮讨论，反复修改直到用户认可；用户明确同意后才问「是否开工」，
  得到开工指令后走第 13 条并行开发流程。
- 禁止听完需求描述就立刻动代码。
- 顺序：第 17 条（方案评审定稿）在前，第 13 条（开工方式）在后，两道都过才动工。
- 例外（免评审稿，但不免并行分支）：纯修复类改动（明确 bug、报错、格式问题、
  用户已给明确指令）；基建/文档类改动。
- 拿不准算不算「功能」时按功能处理，先出方案。

- 状态可查：`scripts/看板.sh` 「已开工」栏打印测试档一致性。
- 同步失败 = 不许汇报。
- 同步方式 = **增量同步**（不清空整目录）：只覆盖同名文件并补新增，不自动删除
  桌面残留；有额外文件则校验失败并列出，按清单确认后单独清理。

## 20. 反馈处理铁律：先分类 → 再阅读 → 再规划

处理任何一批用户反馈必须按此顺序，不许跳步：

1. **分类**：逐条归入四类，判据优先级 垃圾 → bug → 新功能建议 → 其他：
   - bug：现有功能出错/不生效/与预期不符；
   - 新功能建议：想要现在没有的能力；
   - 垃圾反馈：纯数字/符号、无实质内容、明显测试内容、同文本 ≥3 次刷屏；
   - 其他：有内容但不属以上三类。
   按内容判定，与用户自选的 `type` 字段不是一回事；不一致时标出真实分类。
2. **阅读**：分类确定后才生成会话内图文并茂 HTML 阅读页
   （`scripts/生成反馈阅读页.py`）；垃圾不进阅读页。
3. **规划**：阅读页出来后逐类出修复方案（bug 优先），每条写清
   现象/根因/修法/需用户拍板项。

**评审结论出口（落在 `开发待办.md`，`scripts/看板.sh` 同步展示）**：

| 评审结论 | 去向 | 栏位 |
|---|---|---|
| bug · 能当场修好 | 直接修掉，登记待推送 | `## 待推送` |
| bug · 该修但当场修不好 | 记入「bug 待修复」；修完删条目转待推送 | `## bug 待修复(评审通过 · 未修)` |
| 新功能建议 · 值得做 | 记入「计划中」等排期 | `## 计划中(评审通过 · 待开工)` |
| 计划中 · 已开工 | 移入「已开工」；回收后删条目转待推送 | `## 已开工(分支已建 · 待写码)` |
| 建议 · 评审否决 | 不记（会话里说明理由） | —— |
| 垃圾反馈 | 不记、不进阅读页 | —— |

**看板四栏结构与呈现**：
- 四栏 = 待推送 / 已开工 / bug 待修复 / 计划中。
- 流转：计划中 --(开工)--> 已开工 --(回收)--> 待推送；「已开工」原则上不回
  「计划中」（放弃 = 直接删条目，去向写章末引用块）。
- 对话内汇报看板一律用表格、按分类拆成多个独立表格；条目完整全文；
  计点明细并入待推送表，工作树状态并入已开工表；在线版号、测试档同步状态等
  一并呈上不省略。
- 看板每行都必须是「还要动手的活」：已放弃修复的、已修完转待推送的，不许以
  `- （…）` 括注形式占行；去向写章节末尾引用块，细节归 `开发日志.md`。
  `scripts/看板.sh` 会跳过以 `（`/`(` 开头的条目（防手误兜底，不是允许写占位）。
- 这几章只收「评审通过」的项；未经评审的反馈留在日报/阅读页，不直接塞进看板。

**自动化边界**：分析可以自动，执行必须等定夺——
- 可以自动：分类 → 阅读页 → 评审分析 → 登记进 `开发待办.md` 对应章。
- 禁止自动：修 bug、开发新功能、改扩展本体任何代码，一律停在分析，
  等用户看过分析明确拍板后才动工。

**评审分析的汇报形态 = 单文件 HTML**（本地 `output/`，`present_files` 打开）：
- 一页齐四块：反馈原文（原样）、自动归类（与自选 type 不一致时两者都标）、
  评审意见（现象/根因/修法/拍板项）、修改计划（去向）。
- 图片 base64 内嵌、可点击放大、本地零 jpg 落盘。
- 位置命名：`output/评审汇报-YYYY-MM-DD.html`，同名覆盖不累积。
- 与图文阅读页合并成同一份 HTML，一天不出两份。
- 实现：`scripts/生成反馈阅读页.py` 的 items JSON 增可选 `review` 字段；
  无 review 时退化为纯阅读页。
- 聊天里汇报压到最短：一句文件路径 + 待拍板项清单。

## 21. 消息盒子/状态栏文案一律三段式：来源 ｜ 值 ｜ 结果数

凡进消息盒子的消息与状态栏一切提示，文案结构一律三段：`来源(弱) ｜ 值(强) ｜ 结果数(弱)`。

- **必须带来源**：调用时给 `source:'<来源词>'`，缺来源 = 不合规。
- **来源词表（现有 23 个；新功能按功能名补一个 4~6 字词，先登记再写码）**：
  全能搜索 / 回车定位 / 搜索白幕 / 序号定位 / 库存清零 / 货号复制 /
  上滑到顶 / 下滑到底 / 页面滚动按钮 / 抓手光标 / 隐藏元素 / 名称换行 /
  调试模式 / 回放下载 / 大屏跳转 / 自动刷新 / 自动切商品页 / 下架删除 /
  活动广场 / 自动循环讲解 / 粘贴加车 / 明细跳转 / 福袋。
  登记取 label 主干词；label 改名时同步核对映射；以代码实际用词为准。
- 来源词由调用方传入，不写死在渲染层；多入口共用流程按发起方动态给。
- 三段弱化只靠字号 + 灰阶，不加底色：来源 11px `#9aa1ab` / 值 12px `#1f2329`+600 /
  结果数 11px `#9aa1ab`；竖线 1px×10px `#e6e4de`（`.dyb-status-sep`/`.h-sep`）。
  竖线只在带来源的消息上出现。
- 开关回声写法：`source='XX'` + 值 `'已开启'/'已关闭'`（正文不留冒号）。
- 开关回声「首次不出声、之后必出声」：初始态读到时就要记 `prev`，
  不能只靠订阅回调赋值（否则首次拨开关被误判静默）。
- 进度消息也要带来源：`库存清零 ｜ 商品短名 ｜ 正在清零 1/3`。
- **值段放「谁/什么」，不放计数与过程状态**：轮次、序号、进度、成败进右端弱位。
- **成功结果词进右端弱位**：值段只写对象；`已复制/已完成/已关闭` 进 `count` 槽，
  三段要齐全。带 `count` 的结果消息必须加 `standalone:true`（防原地合并丢条）。
- 盒子条目与消息条同一套口径：`pushHistory` 存 `{source,text,count}` 三段，
  渲染各自弱化，不拼纯文本。
- **报错文案「条上短、盒子里全」**：长文案走 `opts.full`；条上 ≤24 字。
  长消息默认摘要 + 点击「查看详情」展开全文（`details/summary` 原生折叠，
  `full` 超 96 字自动折叠；`details:true` 可让短详情也折叠）。
  批量汇总中段写选中范围、右段写结果数；失败按相同原因分组。
  库存操作前为 0 的结果用「无需清零」。
- **盒子容量**：`.dyb-history` 宽 340px、高 420px（矮屏 `min(420px,56vh)`）；
  条目正文不做行数截断（`display:block` 自然换行 + `-webkit-line-clamp:unset`
  + `text-overflow:clip`），条目内选择器一律加 `#dyb-status-bar` 前缀提权；
  列表 `flex:1 1 auto; min-height:0`。
- 条目色点六色齐（含 `.h-alert`），与 `.dyb-dot-*` 同名同色。
- 同一条消息 60 秒内只入盒一次（同 type+来源+文案只刷时间）。
- **「报不报」的纪律：一次打开页面只出一条结果消息，但这一条必须在**：
  成功 = 整条链路合成一条；用户主动接管 = 只说前半个事实（info，不进盒子）；
  失败/异常 = 必须出声（alert 进盒子）；「最多一条」由同一个闸门
  （`takeSpeech()`+状态位）结构保证；不许为凑一条而谎报；不许静默失效。
  判据：这条提示说的是这次的结果吗？是 ⇒ 报且只报一条；只是报过程 ⇒ 不报。
- 与第 16 条配套：16 管「统一 + 收录」，本条管「文案结构与来源词」。
- **盒子覆盖范围**：凡有交互功能的页面都要有盒子（商品列表、中控台两入口、
  罗盘直播明细、罗盘商品列表、直播回放两页、直播大屏）；全域轻量条目不装。
  样式在 `src/content/msgbox.css`（页面不带 style.css 时单独加载它 + dialog.js）；
  回放两页 `say()` 优先转发 `setStatus`。

## 22. 弹窗展开交互：开关门控 + 名字触发，默认不展开

- **开关 = 门控**：开 ⇒ 名字可点、显 ▶、内容仍收起；关 ⇒ ▶ 隐藏、名字灰不可点、
  子项 `pointer-events:none`。
- **名字 = 触发**：展开/收起只由点名字翻转；默认一律收起（渲染期与初态回填
  都不许自动展开）。
- 折叠状态不记忆，每次打开弹窗都收起，不写 storage。
- 判据唯一来源 = `popup.js` 的 `hasSubPanel(meta)`，别处不另写一套。
- 一级行（`foldHost`）一律带开关，没有「无开关的纯分组行」。
- 行内标签只写名字；问号按第 25 条只保留用途与一条关键限制；
  危险操作后果在执行确认处显式展示；徽章在 `<label>` 里时必须拦下 click。
- 实现锚点（别造第二套）：`hasSubPanel()`、`attachHelpBadge()`、
  `attachSubPanelToggle()`（setGate 与 setExpanded 严格分离）、
  `renderFlags()` 的 `foldOpeners`（初态只回填门控）、`popup.html` 的
  `.caret` 三态与 `.row--gated-off`。
- 禁止：开关 change 顺手展开；渲染期/初态回填自动展开；行内「—— 说明」式注解；
  纯分组行。
- 改弹窗后自检至少覆盖：渲染期全收起、开关开不自动展开、点名字才展开、
  开关关连带收回且点不动。
- 本条与第 15、16 条同级，属默认开发规则。

## 23. 读取页面数据：必须剔除「扩展自己注入的节点」

- ❌ 禁止直接用 `el.innerText`/`el.textContent` 正则匹配「标签+值」——
  会把扩展注入的文字算进去。
- ✅ 一律走 `textWithoutExt(root)`：TreeWalker 遍历文本节点，遇带
  `data-dyc-ld-btn`/`data-dyc-code-btn`/`data-dyc-idbtn` 的节点整棵跳过。
  两份实现同口径：`src/live/copy-code.js` 与 `src/live/live-detail.js`。
- ✅ 判据用结构标记（`data-*` 属性），不用按钮文案（按文案认 = 按钮改名就复发）。
- ✅ 取值范围能收窄就收窄：先收到「商品信息」单元格/「复制 ID」按钮父容器，
  读不到才退整行；两道范围都必须已剔除扩展节点。
- ✅ 兜底值校验：从「标签取值」路拿回的值必须确认出现在纯页面文本里，否则丢弃。
- ⚠️ 不用 `Element.matches()` 做这层判定（老内核兼容面）；用 `getAttribute` 逐个判。
- 自测：`node scripts/自测-货号取值.js`（27 用例；从源文件抠函数源码跑）。
  新增读取页面字段的功能时照此模式补一份同类自测。
- 不改的口径：`isCodeLike` 的「3~30 位字母数字」不动，纯数字货号照读。
- 本条与第 21 条同级，属默认开发规则。

## 24. 被提前调用的函数里，`const` 必须声明在任何调用点之前

- 函数声明会提升、`const`/`let` 不会；本项目 `fastWait`/`waitFor`/
  `requestAnimationFrame` 的第一拍是同步的，回调可能在 `const` 初始化前被调到。
  判据：写完函数回头看「谁会提前调用它」，凡它引用的 `const`/`let` 一律声明在
  最早调用点之上。不指望「回调都是异步的」。
- **任何异步链路起点必须有 try/catch 收尾**：凡 `busy=true` 之后才启动异步流程的，
  启动语句外包 try/catch，catch 里至少做三件事：清 busy → 复原 UI 状态 →
  报一句人话。宁可多一条「已中止」，也不能让功能静默变砖。
- 同理适用任何状态锁（busy/running/inFlight/pending）：置位与复位必须在同一条
  可达路径上；跨回调时加超时兜底或 try/catch 兜底。

## 25. 文案必须说清用途、结果与限制；新增功能按同一规则审查

本条是产品文案与审查的现行规则（第 16/21 条的消息接口与收录规则继续生效，
本条统一文字内容）。改规则时替换原条款，不追加冲突口径。

**写之前先核对功能**：逐项记下「在哪页、用户做什么、程序做什么、影响哪个对象、
何时停止、失败怎么处理、是否改数据」。每条承诺必须能指向实际实现或行为测试；
没有证据的速度/效果/兼容性保证不得写入；静态分析结论注明验证边界。

| 位置 | 必须讲清 | 长度与边界 |
|---|---|---|
| 开关名/按钮名 | 功能或动作，用用户在页面上能找到的词 | 功能名 ≤12 字；按钮优先动词+对象，不为凑短省掉「删除」等实际动作 |
| 问号第一句 `desc` | 开启后能做什么 | ≤32 字，一句一个主要动作 |
| 问号第二句 `note` | 一条最重要的限制/风险/停止条件 | ≤24 字；`desc+note` ≤56 字（含标点空格） |
| 按钮悬停说明 | 点击会发生什么 | 一句话为限；不复述开发过程、不列算法步骤 |
| 确认框 | 对象、数量、真实动作、不可撤销后果 | 清零/下架/删除的风险在执行确认处显式展示 |
| 结果消息 | `来源 ｜ 对象 ｜ 结果或数量` | 中段只写对象；长原因走 `full`。`full` 只装两种：条上放不下的长原因、同一对象的另一种称呼；不装内部标识 |
| 更新说明 | 「上一个已发布版 → 本版」的净差异；同一能力压成终态 | 摘要 ≤30 字；要点 1–5 条、每条 ≤48 字；本周期新引入的能力不得写「修复」 |

**更新说明的基线是上一个已发布版，不是上一批开发动作**：同一能力在本发布周期内
断断续续改了多少轮，客户都只是第一次见到它 —— 这类返工一律合并成一句「它现在是
什么样」，不得出现「修复 / 优化 / 调整 / 不再」。只有上一个发布版里已经存在的能力，
才允许写「修复」。判据在 `scripts/check-product-copy.js` 的 `checkNewsBaseline()`，
能力词表见 `scripts/changelog-entities.json`（新增用户可见功能时补一行）。
**措辞问题不拦发布**（用户 2026-11-05）：发布脚本 0/6 先自动删掉不属于本版净差异
的条目并提交，其余措辞问题降为警告；只有「缺少一句话」「要点 0 条」这类会让更新页
空白的结构性缺陷才中止。**新增功能的描述不会被自动删除**：同一功能既写了新增又写了
修复时删掉修复那条，只写了修复口吻时保留原文并提示改写成「它现在能做什么」——
删了商家就不知道这版多了什么，比写得不好更糟。

字数为硬上限（按 Unicode 字符计）；阈值的机械检查只定义在
`scripts/check-product-copy.js` 的 `limits`，改阈值必须同步本表。
超长先删重复与实现细节；真实风险写不下时移到确认框或说明面板，不能删风险凑字数。
标点与断句：开关问号一律全角标点，`desc`、`note` 各自以「。」收尾；
一句一个动作。控件位置只在用户找不到时才写。

**内容审查必须逐项通过**：

1. 先说用途，不写实现描述、不在问号里回顾旧版怎么错。
2. 每处只回答当前问题；同一事实不在父子提示重复；长教程归设置面板或 README。
3. 风险与承诺准确：不把平台「数据异常」无条件称正常；不写与实际功能矛盾的
   全称承诺；数据说明区分日常操作、更新联网、主动反馈上传、调试采集。
4. 结果不抢报：写入成功才说「已保存」；部分成功/未执行/用户取消/网络不明
   分别说明，不一概而论。
5. 三段语义固定：单一对象用对象名；无对象开关回声中段「已开启/已关闭」；
   批量动作中段「选中商品」、右段写数量与结果。来源用已登记主干词。
6. 统一术语：商品 ID 与货号/款号分开；弹窗、页面按钮、帮助、消息、README、
   更新说明同时核对。
7. 更新说明按功能合并，只写最终效果；根因、提交号、断言数与修改过程写
   `开发日志.md`。
8. 规则可交接：现行规则只在权威条款维护；必跑检查必须入库，不引用 `.tmp/`
   或本机缓存脚本；模板示例也要满足规则。

**程序审查同步执行**：异步写入等待结果、失败恢复界面；重复点击只执行一次；
停用/离页/用户接管后旧异步任务不得继续点击；共享设置写入核对并发覆盖；
读页面字段排除扩展节点；反馈草稿与操作历史存扩展私有存储；诊断排除输入框
及可编辑区后代文本，含网址的报错脱敏；定时与观察器有退出清理；新旧浏览器
能力有检测与降级；备份不能静默漏文件，未开始写盘不得触发回退，自动回退
只能用本次完整快照，恢复成功必须核对必需资源。涉及这些问题时增加能区分
正常与异常的行为用例，不以源码包含某字符串代替行为验证。

**固定实现口径**：开关写入统一 `dyc:writeFlag` 后台串行队列；消息历史按
`origin+pathname` 隔离（≤20 页 × 100 条，60 秒相邻同文案去重）；截图绑定
发起标签页与窗口，来源缺失/切页/关闭即取消；更新先建完整快照确认入库再写文件，
写盘未开始不自动回退，更新与回退均逐文件回读校验；发布只推主干和本次标签并
核对远端完整提交哈希；观察器只为有关变动唤醒，同一拍复用布局矩形。

**执行与证据**：
- 改 `flags.js` 时，`wt-merge.sh` 自动相对分叉点跑
  `node scripts/check-product-copy.js --gate`；发布前再查整批与更新说明。
  它查长度/结构/重复/部分错误承诺，不能判断语义，仍须人工对照代码。
- `--gate` 对全部命中返回非零；`--base <本地发布标签> --gate` 仅豁免该标签中
  原样存在的旧问题。禁止改基线、删规则、自动截断文字或删断言以取得通过。
- `publish.sh` 已接入该增量检查；检查器失败、读不到元数据或基线无效都必须报错。
- 收工报告写清：已审哪些、确认问题、静态疑点、已改哪些、未改哪些、测试结果；
  源码语法、模拟环境测试、真机验收分开表述；任何失败不得包装成「全绿」。

## 26. `README.md` 只写给小白看：这是什么程序、有什么用

适用范围：Gitee 仓库首页的 `README.md`。详细用法一律进 `使用手册.md`，
两份文件分工固定，不合并、不互相复制段落。

**结构（四块，顺序不变）与硬指标**：

1. 一句话是什么（给谁用+干什么），紧跟一行当前版本号（不许删，`publish.sh` 校验）。
2. 它能帮你做什么：要点 ≤8 条、每条 ≤20 字，句式「动作+结果」；不凑数、不删真实功能。
3. 怎么装：≤4 步，一步一句，只写必做动作。
4. 用之前要知道：≤2 条，只写后果（会改真实平台数据、清掉不可撤销、只在当前浏览器生效）。

全文 ≤60 行、≤500 汉字；超了删内容，不把句子压得更难读。

**必须挪进 `使用手册.md`、README 一律不出现**：开关/参数清单、默认值、分组明细、
页面 URL 表；灯色状态表、重试间隔、失败上限、滚动定位策略；存储条数与保留页数、
迁移清理规则、诊断与隐私细节；更新/回退流程、备份份数、快照与哈希；术语区分、
异常判读方法；一切技术名词。

**写法**：说「你」；用商家的词（小黄车、库存、货号、回放）不用实现词；
不写技术句式；除功能条数外不做数字承诺；不写「本版新增 X 项」——
换版本只改那一行版本号。

**改 README 前三条自检**：有没有混进禁止项（有就移到手册，不留残句）？
功能有没有被「精简」掉（只有真下线才删条目）？新增功能是否先在手写全细节、
README 只加一行要点？

**判据**：没用过的人读 30 秒能说出「这是给抖音商家用的浏览器小工具，能清库存、
自动加车、自动续讲解」，且没有需要追问的技术点。

## 27. 弹窗布局与平台数量解耦：新增平台只加数据，不改样式

「内容少 → 中间留空 → 调试模式/版本号黏在窗口最下方」是任何功能少的平台
都应有的表现；以后加新平台行为必须自动一致。

**新增一个平台只做一件事**：在 `src/content/flags.js` 的 `DYC_PLATFORMS` 加一项
（id/label/groups/urlRe），再把分组 id 加进 `DYC_FLAG_GROUPS`；
弹窗样式、页脚、平台胶囊一个字节都不用改。

**布局铁律（`src/popup/popup.html`）**：

| 位置 | 必须 | 绝对不许 |
|---|---|---|
| `html`/`body` | `height:600px` | `max-height` |
| `body` | 纵向 `display:flex` + `overflow-y:auto` | —— |
| `.pop-head`/`.tagline`/`.pop-body` | `flex:none` | `flex:1` |
| `.pop-foot` | `flex:none` + `margin:auto 16px 12px` | 任何 `position:fixed/sticky` |

原理：页脚 `margin-top:auto` 只在有剩余空间时生效——内容少则黏底、内容多则
跟在内容末尾滚到底才见，两种表现同一行 CSS 产生，不按平台写分支。

**明令禁止**：为某平台写专属样式（平台差异只体现在显示哪些分组）；
给 `.pop-body` 加 `overflow-y`；用 `position:fixed` 实现页脚沉底。

**守卫**：`scripts/自测-弹窗面板.js` 已把上表钉成断言；新增平台后
`scripts/自测-弹窗平台切换.js` 检查每个分组都被平台认领。
