### 页面匹配：中控台有**两个**域名入口（2026-10-11 补）

抖音电商的直播中控台不是只有一个地址 —— 商家和达人各有一套，功能大体相同：

| 角色 | 入口域名 | 路径 |
|---|---|---|
| 商家 | `fxg.jinritemai.com`（抖店） | `/ffa/content-tool/live/control` |
| 达人 | `buyin.jinritemai.com`（巨量百应） | `/dashboard/live/control` |

**两个都要认。** 2026-10-11 用户报障「抖店中控台生效、巨量百应中控台不生效」，
根因就是 `manifest.json → content_scripts.matches` 只写了抖店域名 ——
内容脚本根本没注入,页面上连左下角「DY-COCO」标记都不会出现。
（判据：**「插件完全不生效」+ 没有左下角标记 = 没注入 = 查 matches**。）

改页面匹配时**必须同步这 5 处**，漏一处就会出「有的页面行、有的页面不行」的怪象：

| 位置 | 作用 |
|---|---|
| `manifest.json → content_scripts[].matches` | 决定**是否注入**（最关键，漏了全盘失效） |
| `manifest.json → host_permissions` | 让扩展有该站点的访问授权 |
| `src/content/flags.js → DYC_PAGE_PATTERNS` | 各功能「作用页」判据 + 弹窗「已应用到 N 个页面」计数（弹窗直接读它，没有第二份副本） |
| `src/content/anchor.js` 里的页面正则 | 决定左下角「DY-COCO」标记与调试态（**仅**已注入该脚本的页面） |
| `src/live/nav.js` 的路由守卫 `/live\/control/` | 决定 SPA 路由切回中控台后是否补插控件 |

⚠️ `matches` 的路径**必须带 `*`**：中控台地址后面总跟一长串埋点参数
（`?btm_ppre=…&btm_show_id=…`），不带通配符的路径是**精确匹配**，会漏掉真实地址。

⚠️ 百应入口的工具栏文案可能与抖店不同，故 `nav.js` 的锚点查找做了
**两段式**（前期只认「筛选」、后期才放宽到备选文案），详见组件详解。

> 第一版按 2022–2023 年的旧资料把「微信小店后台」写成 `channels.weixin.qq.com/shop`——
> 那是**视频号小店**时代的地址。微信小店 2023 年后已独立，官方资料库、2026-09 新规公告、
> 商家教程里的后台入口统一是 **`store.weixin.qq.com/shop`**（`store.weixin.qq.com/` 与
> `/shop` 返回同一个登录页 `wx-shop_loginIndex`，SSR + `#app`，无 iframe、无 CSP）。

| 约束 | 具体表现 | 对策 |
|---|---|---|
| 查询 | `document.querySelector` 只摸得到壳 | `host.shadowRoot.querySelector(...)`，或复用 `page-probe.js` 的 `deepQuery()`（已支持穿透 open shadow，2026-10-31 新增） |
| iframe 沙箱 | micro-app 另有 **iframe 模式**：内容在 `about:blank` 的 document 里，此时 shadow 内可能是空的 | `deepQuery()` 已一并穿透**同源** iframe（`iframeDocOf()`）；跨域读不到，报告里标「跨域，读不到」 |
| 样式 | **manifest 里登记的 content css 不会进入 shadow root** | 单元素改样式**优先写内联**（`el.style` 跨 shadow 天然有效，见下节）；只有需要批量规则时才 `shadowRoot.appendChild(<style>)`。`insertCSS` 两处都无效 |
| 重建 | 微前端在路由切换 / 列表刷新时可能重建 shadow 内容，注入的 style 与监听会一起消失 | MutationObserver 守护宿主或 shadow 子树，与抖店的 SPA 重建同类 |

closed 模式的 shadow root 读不到（`el.shadowRoot` 为 null）；micro-app 当前是 **open**（能读到）。

| 事 | 结论 |
|---|---|
| 截断形态 | 实测**只有** `white-space:nowrap` + `text-overflow:ellipsis`：盒子 288×20、文本宽 321–447、文本高/可见高 20/20，**没有行数钳制** ⇒ 解除 nowrap 后自然折行，**不需要动列宽、不需要加宽表格** |
| 穿 shadow 的方式 | 用**内联样式**（`el.style.xxx`），不是 `shadowRoot.appendChild(<style>)`。内联样式属于元素自身、跨 shadow 天然有效；改哪个元素一目了然，还原时也不留一张残留样式表。「必须插 style」只在需要**批量规则**时成立 |
| 脚本自带穿透 | 常驻功能**不能**依赖 `page-probe.js`（它是按需注入的一次性采集工具，不在常驻注入列表里）。`wx-goods-title.js` 自带 `collectRoots()`：document + open shadowRoot + 同源 iframe 三路下潜，深度 6 / 节点预算 2 万，只在定位阶段调用 |
| 认元素 | **语义类名 `.goods_title_1` 优先**，命中数为 0（平台改版）才退回行为特征扫描（横向溢出 + 像名称 + 行内第一个）。一上来就扫特征会把同行的「规格」「时间」列一起展开、把不相关的列撑高 |
| 跨 realm | iframe 内元素要用**它自己文档的** `getComputedStyle`（`el.ownerDocument.defaultView`），主文档的量出来是空值 |
| SPA | 脚本注入整个 store 域，内部按 `location.pathname` 判页；1 秒轮询比 `href` 发现路由变化 → 缓存作废重定位。**matches 不能只写 `/shop/goods/list`** —— 前端路由从菜单点进去不会重新注入，那样永远不生效 |
| 幂等 | 标记 + **计算值**双条件（沿用 name-wrap 2026-10-15 教训）：平台重渲染会抹掉内联样式、留下陌生属性标记，只看标记会「永不补涂 → 永久省略号」。重写时**不重复备份**，否则备份里存进的是我们自己写的值 |
| 行高 | 名字折行会让该行变高 —— 「完整显示」的必然代价，开关 note 已写明，不隐瞒 |
| 折行留白 | 只对**折成两行以上**的名字加：`line-height:1.55` + `text-wrap:balance` + `padding-bottom:2px`。单行保持平台原样。`text-wrap:balance` 让两行长度接近（Chromium 114+ 才支持，老内核静默忽略、回退普通折行，无副作用）；窗口拖宽使两行变单行时，由 `resize`（防抖走 `scheduleApply`）触发一次残留留白清理 |
| ⚠️ 改样式要升标记版本 | `MARK` 的值就是「处理到第几版」，当前 `'2'`。给已上线功能**追加**样式时必须升版本号，否则老元素已满足幂等条件、**永远拿不到新样式**（浏览器里跑过 v1 的元素会一直停在旧样子，看起来像「改了没生效」） |

#### 微信小店第二个功能：商品行快捷复制（货号 / 商品链接，2026-10-31）

`src/content/wx-goods-tools.js`，挂条目 [8]，排在 `wx-goods-title.js` 之后、`debug-panel.js` 之前。
开关 `wxRowCopy`（「商品行快捷复制」，微信小店组），作用页 `wxGoodsList`。
两个按钮插在「规格/编码 预览 分享」那一行（`findMetaRow()`：行内文本恰为「分享」的叶子元素的父容器）。

| 事 | 结论 |
|---|---|
| 货号的定义 | **= 「规格/编码」弹层里商家 SKU 编码的第一个分隔符之前那一段**（用户 2026-10-31 定：`NE1C1142W-35-38` → `NE1C1142W`，分隔符含 `-` `_` `／` 及全角）。商品名末尾常写、但**会漏写**；SKU 一般不会 ⇒ **SKU 是权威源，名字只是便道** |
| 货号三级取号 | ① 页面数据（Vue 组件里按商品 ID 精确匹配该商品对象，读 `sku_list[].sku_code`）→ ② 商品名末尾切段 → ③ 点开「规格/编码」弹层读全部 SKU 编码再切段。前两档零点击，第三档会闪面板，且**只在①②都没有时才走**；读到后按商品 ID 缓存 10 分钟，同一商品不重复开弹层 |
| 弹层怎么定位 | 平台没给稳定类名 ⇒ 按内容找：先找「商家SKU编码」标题的文本节点，再从它逐层向上，取「编码个数最多、文本不超过 3000 字」的那层容器。不设文本上限会一路爬到 `body`，把页面上别处的代码文本一起扫进来 |
| 多 SKU 不一致 | 优先取与商品名末尾一致的那个，否则取出现次数最多的；不一致写进调试日志（`__dycDiag.note`），不闷着 |
| 商品链接**拼不出来** | 官方文档与社区实例一致指向 `https://store.weixin.qq.com/shop/a/<短码>`，短码与商品 ID 无可推算关系 ⇒ **不要试图用 goodsId 拼 URL**，那是错的 |
| 链接怎么做到"一键" | **L1：从 Vue 组件实例里按商品 ID 精确匹配商品对象**，取其链接字段，零点击零闪烁。⚠️ 不能用「包含」匹配 —— 列表容器对象含全部商品 ID，会先命中它、再取到**第一个**商品的链接；找不到对应关系就放弃，宁可退兜底也绝不取错 |
| 兜底 L3 | L1 拿不到才模拟点击：点「分享」→ 100ms × 30 轮（3 秒）→ 读 `input/textarea.value` 与面板文本 → 派发 Escape 关面板。命中白名单收窄到 `store.weixin.qq.com/shop/` 且排除列表页自身。轮询别只给 1.2 秒 —— 首次打开面板组件还没渲染完就超时（用户报的「第一次必定失败」就是这个） |
| 成功消息只说结果 | 用户 2026-10-31：「不用告诉我兜底」⇒ **成功消息不交代取的哪条路**，只报值：`货号复制 ｜ 已复制货号 NE1C1142W`、`商品链接 ｜ 已复制商品链接`。失败才说原因（`没取到货号`）。单条复制**不传 `count`** —— 传 `'1'` 会在右端渲染成一个孤零零的 1，读起来像「1 个」 |
| ⚠️ 已废弃的 L2 | 「扫页面里隐藏的 input 取链接」看似可行，但分享面板几乎都是**全局单例**：面板里留的是上一次分享的**别的商品**的链接，扫全页取第一个 ⇒ 给 A 复制了 B 的链接。用户粘贴出去才发现发错货，比取不到严重得多。已删除 |
| 剪贴板顺序 | **先 `execCommand` 再 Clipboard API**。本扩展 permissions 只有 `clipboardRead`、没有 `clipboardWrite`，`navigator.clipboard.writeText` 在这种上下文里可能 reject、**更可能挂起不 settle**，`done` 永不回调 ⇒ 按钮卡在「点了没反应」。execCommand 同步返回成败，反馈不迟到（抖店那几处货号按钮能工作，靠的也是它） |
| 按钮点击绑定 | 同一元素上**捕获 + 冒泡各绑一份**，用 `fired` 去重 —— 平台可能在捕获阶段截断事件（2026-10-25 渠道品按钮踩过同类） |
| 关面板 | 只派发 `Escape`（keydown + 80ms 后 keyup）。**不点遮罩** —— 可能点到页面上别的按钮，风险大于收益。关不掉时如实提示用户手动关，不假装 |
| 插入位置的空间问题 | 那一行 288px 已被「规格/编码 预览 分享」占满，两个按钮（44+62+6）放不下 ⇒ 给容器补 `flex-wrap: wrap`（放得下时无行为变化、放不下才换行），**绝不让按钮溢出压到右侧价格列**；关开关时这条一并还原 |
| 与「商品名完整显示」的边界 | 按钮带 `data-dyc-wx-btn` / `data-dyc-wx-btnwrap`；`wx-goods-title.js` 的 `isExtNode()` 已认这两个属性 —— 否则「复制链接」四个字满足「≥4 字、像名称」，兜底扫描会把它当商品名展开 |
| ⚠️ 未实机验证 | 分享面板的真实 DOM 结构（开发时无法登录商家后台）。若平台把链接藏在 JS 变量里、DOM 里不出现，功能会如实报「取不到」，不会复制错东西。面板会闪 0.2~1 秒，这是「没有接口只能模拟点击」的代价 |

- **判据是域名族，不是枚举子域。** 第一版写成 `(?:fxg|buyin|compass)`，
  用户当天纠正为「`jinritemai.com` 这个统称抖店」—— 枚举的毛病是
  「平台加一个子域就得回来改代码」，而用户要的是「全抖店」。
  正则 `(?:[a-z0-9-]+\.)*jinritemai\.com` 天然排除 `notjinritemai.com`
  与 `jinritemai.com.evil.com` 这类近似域名（必须有「点 + jinritemai.com」才算数）；
  `manifest.json` 侧对应 `https://*.jinritemai.com/*`。
- 排除中控台用的是正则**负向先行断言**，原因写在 `flags.js` 的注释里：
  不排除的话，用户取消勾选「中控台智能助手」却仍勾着「抖店智能助手」时，
  抖店那两条规则会顺手把中控台的助手也隐掉（勾选与实际行为对不上）。
- **注入策略是「单开一条轻量条目」**：`manifest.json` 第 3 个 `content_scripts`
  只带 `flags.js + hide-elements.js`，并用 `exclude_matches` 排掉上面三个专属路径
  （避免与既有两条重复注入）。**不要**图省事把 `shopAll` 塞进商品列表页那条 ——
  那会把「DY-COCO」标记、抓手光标、清空库存整套脚本注入到无关页面。
- `host_permissions` 与 `web_accessible_resources` 的 matches 同步用域名族通配，
  这样反馈浮层的资源在任意抖店子域都能加载。
- **活动广场（2026-10-25 补）**走**单独一条** `content_scripts`：
  `matches = https://fxg.jinritemai.com/ffa/merchant/*`，带 flags / diag / anchor / dialog /
  campaign-channel-tick / hide-elements。为什么取整个 `/ffa/merchant/` 而不只写
  `parent-campaign-detail` 一条路径：活动广场列表与父活动详情同属一个 SPA 模块，
  平台切换走 `pushState`（不刷新页面），content_scripts 只在导航时注入 —— 卡死单页路径
  会出现「从列表点进来功能不生效」（直播回放 2026-10-18 踩过同一坑）。同时把
  `https://*.jinritemai.com/ffa/merchant/*` 加进全域条目的 `exclude_matches`，避免重复注入。
- ⚠️ 该条目**没有入口脚本**（`hide-elements.js` 是自启动 IIFE），
  这属于约定允许的「轻量条目」，白名单在 `scripts/check-manifest-order.py`
  的 `SELF_BOOTING`；**普通功能脚本仍必须挂在入口脚本之前**，不要照抄这种写法。
- **直播大屏 `/screen/live/*` 是第四条专属条目**（2026-10-18 用户要求「消息盒子也要支持
  直播大屏的页面」）：它要带 `dialog.js`（状态条 / 消息盒子）与 `msgbox.css`（盒子外观），
  而全域轻量条目按设计只带 flags + hide-elements ⇒ 单开一条 `content_scripts`，
  同时把该路径写进全域条目的 `exclude_matches` 防双注入。
  （该条目还带 `style.css`：确认弹窗 / 隐藏元素那套在里面。
   **消息盒子外观只认 `msgbox.css`**,改盒子别去 style.css 里找。）
  ⚠️ **不为它新增页面模式键** —— `shopAll` 已覆盖（全域正则只排除中控台两个入口）。
  「属于哪个页面模式」与「带哪些脚本」是两件事：前者决定功能是否生效，后者决定注入了什么。
- **直播回放的注入范围是 `anchor.douyin.com/*` 全域，不是 `/anchor/review`**
  （2026-10-18 用户报「从别的页点按钮切进复盘页、不刷新就不出下载按钮」后改的）：
  `content_scripts` **只在导航时注入**，而这套后台切页走 `history.pushState`，
  根本不算导航 ⇒ 若 matches 卡死在 `/anchor/review`，从别的页切过来时页面上
  一个脚本都没有，切到复盘页也不可能有按钮（只有刷新撞上时机才行）。
  现在注入放宽，**是否显示由 `replay-download.js` 的 `pageKind()` 每拍判一次**：
  非复盘页不挂按钮、连左下角绿标记一起收掉（避免主播后台每个页都挂个空盒子）；
  切页时另用 `hookRoute()` 包 `pushState / replaceState` + `popstate / hashchange`
  催一拍（80ms 去抖），按钮 0.1 秒内就出来，2s 轮询只作兜底。
  ⚠️ **不要为了「省注入」把 matches 改回 `/anchor/review`** —— 那会重犯这个 bug。
  代价说明：这套脚本在 anchor 各页都会加载（`replay-net` 只挂 PerformanceObserver、
  候选上限 400 条；`mux.min.js` 约 400KB 只解析不执行），实测开销可接受。
- ⚠️ 抖店各页面用的是同一套组件库，`.index_wrapper__3UiS6` /
  `.feedbackEntrance-Okk7KM` 一般通用；若某个页面「勾了却不隐藏」，

  不要动已生效的那条。
  **⚠️ 2026-10-15 收窄：这两条选择器在「中控台」上都不成立** ——

  `.feedbackEntrance-Okk7KM` 也不在中控台（它本就被 `shopAll` 排除）。
  **组件库同源 ≠ 每个页面都渲染同一个组件** —— 详见下面「中控台两个入口必须各自核对」。

1. **导航菜单条**：百应没有这个组件（兜底取 0，用户实测无感 ⇒ 不修）。
2. **智能助手浮层**：百应没有；抖店中控台有且已被正确隐藏。

**两条纪律（比结论更重要）：**

- **不得互相类推。** 新增或修改中控台功能时，**两个入口各自核对一遍**；
  只在一侧验过的机制，在文档里明确标注「单侧已验证」。
- **⚠️ 判断「元素是否存在」不能用可见性过滤。** 本扩展的「隐藏页面元素」正是用
  `display:none` 藏目标的 —— 用 `getBoundingClientRect()` 过滤会把
  **已被我们藏好的目标**误报成「不存在」。真机踩过：抖店中控台
  `.index_wrapper__3UiS6` **可见 0 / 存在 1**，差点据此误判「这条规则空转」。
  核对时必须同时给出**可见数 / 存在数**两个值（探针 v4 起已如此输出）。

#### content_scripts 脚本顺序约定（新增脚本必读）

`content_scripts[].js` 是**有顺序要求**的：后面的脚本要用前面脚本定义的全局函数，
顺序错了在浏览器里的表现是「某个功能莫名不生效」，极难定位。
机械闸门：`python scripts/check-manifest-order.py`（不通过退出码 1）。

| 层 | 权重 | 放什么 |
|---|---|---|
| 0 开关定义层 | 0 | `src/content/flags.js` —— **必须第 0 位** |
| 1 基础设施层 | 1 | `anchor.js` / `dialog.js` / `row-scan.js` / `diag.js` / `cursor-fix.js` / `tool-slots.js` / `locate.js` |
| 2 功能层 | 2 | 各功能自己的脚本（**新功能往这里追加**） |
| 3 入口层 | 3 | `main.js`（商品列表页）/ `toolbar.js`（中控台）—— **必须最后一位** |

- 层级权重必须**非递减**，同层内不校验相对顺序、也不允许同一文件重复出现。
- **轻量条目例外**：允许一条 `content_scripts` 只带 `flags.js + 自启动脚本`
  （白名单 `scripts/check-manifest-order.py → SELF_BOOTING`），
  用于「只把一个自启动功能铺到很多页面」的场景（当前仅「隐藏页面元素」）。
- ⚠️ `diag.js` 属基础设施层（2026-10-14 补录）：它要在功能脚本之前挂上错误钩子，
  否则功能初始化阶段的异常它记不到。此前漏登记，闸门一直误报 10 处。

### 各组件详解

**`flags.js` — 必须第一个加载**

功能开关读取层，商品列表页与直播中控台页共用。只提供两个函数：

- `dycReadFlags()` → Promise，返回合并默认值后的完整开关对象
- `dycWatchFlags(cb)` → 订阅 `chrome.storage.onChanged`，拨动开关即时回调

**它只管「哪些功能是开着的」，不管功能本身。**

新增一个开关的完整步骤（照着做，不要另起炉灶）：

1. 在 `flags.js` 的 `DYC_FLAGS_DEFAULTS` 加一项,默认值按口径给
   (调试类 `false`,其余 `true`;最新实例 = `cursorFix`,见 `cursor-fix.js`);
2. 在 `popup.html` **对应的分组框内**加一个 `.toggle-row`,内含 `<input id="flag-xxx">`;
3. 在 `popup.js` 的 `FLAG_DEFAULTS` 与 `PAGE_PATTERNS` 各加一行，
   并绑一个 `change`：`writeFlag('xxx', on)` + `reportApplied(...)`；
4. 在对应内容脚本里用 `dycReadFlags()` 决定初始是否启用，
   在 `dycWatchFlags()` 里按开关分别调用「启用 / 停用」两个函数；
5. ⚠️ **停用必须真的停** —— 除了移除已注入的 DOM，
   还要停掉监听器与定时器（`stopRowWatcher()` 就干这个）。
   只删 DOM 而留着 `MutationObserver`，下一轮渲染又会把 UI 补回来，
   开关等于没关。

**`cursor-fix.js` — 抓手光标可见性修复**

网页无法指定光标颜色 —— CSS `cursor` 走关键字时一律取浏览器内置资源。
扩展能做的是**换掉那个关键字**:`grab` / `grabbing` → `move`
(四向箭头,自带黑描边,任何底色上都看得见,且仍表达「这里可以拖动」)。

难点是「找全哪些元素是抓手」。平台是 React + 微前端:拖拽区可能由样式表规则控制、
被 JS 动态改 class / 内联 style、或写在 `:hover` 里;更麻烦的是平台 CSS 大概率跨域,
此时 `document.styleSheets[i].cssRules` 会抛 `SecurityError`,一条规则都读不到。
因此用**三条互补路径**,任一条命中即生效:

| 路径 | 触发时机 | 覆盖场景 |
|---|---|---|
| A 静态规则 | 遍历 CSSOM,把含 `cursor:grab` 的选择器**原样**翻译成 `!important` 覆盖规则 | 同域样式表;开销 0,且能覆盖 `:hover` 规则 |
| B 悬停实测 | `mouseover` / `mousedown` **捕获阶段**取 `getComputedStyle`(此刻正是悬停态) | `:hover` 规则 + 跨域样式表 |
| C DOM 兜底 | 开局分片扫描 + `MutationObserver` 增量扫描 | 内联 `style="cursor:grab"` |

三条路径汇到**同一个出口**:给元素打属性标记 `data-dyc-cursor-fix`,
由一条属性选择器规则统一接管 ——
`html body [data-dyc-cursor-fix] { cursor: move !important }`
(前缀 `html body` 用于压过平台同样带 `!important` 的规则)。

性能约束(页面节点上万,不能一次性跑 `getComputedStyle`):
- 开局全量扫描按 **400 节点分片** + `requestIdleCallback`;
- 变异合并 **300ms 一批**,避免逐个扫描;
- 延迟补扫 `[500, 1500, 3000, 6000, 10000]` ms
  —— 平台是 Garfish 微前端,子应用挂载后样式表才分批注入。

`disable()` 移除 `<style>` 与两个监听器;元素上的属性标记**刻意保留**
—— 覆盖样式已移除后它不再影响光标,再次开启时无需重扫。

**`anchor.js` — 除 `flags.js` 外必须最先执行**
两个职责合一，所以必须排在 `manifest.json` 的 `js` 数组第一位：
1. **加载探针**:页面左下角创建状态条,显示绿色「DY-COCO」品牌标记
   (**2026-10-11 起不再带「已加载」字样**,只留品牌名)。
   这是判断「扩展是否注入成功」的唯一现场证据。
   调试模式下变橙并追加「(调试模式)」。
2. **定位工具库**（全局函数，供后续脚本调用）：
   - `normalize(text)` 文本规范化：去首尾空白、压缩空格、去全角空格
   - `isVisible(el)` 可见性判定：有尺寸且未被 `visibility/display/opacity` 隐藏
   - `findByText(text, opts)` 按可见文字找元素，支持精确/包含两种模式
   - `findAllByText(text, opts)` 同上，返回全部匹配
   - `findAncestorByText(text, opts)` 向上回溯找祖先，可配`validator`
   - `findProductRows()` 识别商品行（从「编辑」按钮回溯）
   - `extractProductInfo(row)` 提取商品名/ID/货号/总库存
   - `extractTitle / extractProductCode / extractTotalStock` 分字段提取，
     每个都有多种回退策略
   - `isPlausibleTitle / sanitizeTitle` 商品名合理性校验
   - `findByClassPrefix(root, prefix)` 按 class 前缀查找（**只匹配前缀，
     因为抖店 class 末尾带构建哈希，每次发版都变**）
   - `findDashedUnderlineElements()` 找虚线下边框元素（货号、总库存的共同特征）

   注意：`findProductRows` 依赖「编辑」按钮，因为「编辑」是固定文案且数量与商品数一致，
   比从左侧找商品名更稳定。

**`dialog.js` —弹窗与状态条组件库**
- `showConfirmDialog({title, fields, warning, confirmText, cancelText, danger, onConfirm})`
  确认弹窗。`danger=true` 时确认按钮为红色。
- `showProgressDialog()` / `updateProgress()` / `closeProgress()`
  进度弹窗，用于清零过程反馈
- `ensureStatusBar()` 创建左下角状态条容器（幂等，重复调用不会重建）
- `toast(msg, type)` 状态条右侧的临时提示，
  type取 `info|success|warning|error`。成功类3 秒自动消失，失败类常驻

**`row-scan.js` — 行识别与注入调度**
- `injectAllRows()` 扫描并对所有未注入的商品行注入按钮，返回注入数量
- `startRowWatcher()` 用 `MutationObserver` 监听商品列表容器，
  处理SPA 路由切换、翻页、筛选后的重新注入
- `stopRowWatcher()` 关掉开关时调用，**三个句柄都要清**：
  观察器、路由轮询、已排队待执行的注入
- `isOwnNode(node)` 关键：判断节点是否属于本扩展，
  用于**避免把自己的 UI 当成商品行**导致无限循环注入

**`inject-button.js` — 按钮注入与移除**
`injectClearButton(row, editButton)` 采用**四级递进回退**：
1. `insertBelowStockColumn()` 首选，定位到「总库存」表头横坐标下方（用户指定位置）
2. `insertBeforeEdit()` 插在「编辑」之前
3. `insertBeforeOffline()` 插在「下架」之前
4. `row.appendChild()` 直接追加到行尾
`resolveTextNode()` 把大容器节点下钻到真正承载文字的那个节点，保证插入位置精确。
`removeAllClearButtons()` 是 `injectClearButton()` 的逆操作，开关关闭时调用。

**`clear-stock.js` — 清零执行**
- `startClearStock(row, info)` 主流程：确认 → 提交 → 轮询结果
- `isDebugMode()` / `initDebugPanel()` 调试面板（仅调试模式挂载）
  - ⚠️ **调试开关状态是「模块加载时读一次、缓存在变量里」的**：
    不能直接判断 `chrome.storage.local.get()` 的返回值 —— MV3 里它是
    Promise，取 `.dybDebug` 永远 `undefined`（踩坑第 34 条）。
  - 开关的即时生效走 URL 改写（弹窗会直接改地址），
    所以这里不需要监听 storage 变化。
- 关键：`executeClear()` 走**页面自带的官方控件**，
  不调用后台内部接口。平台的清零逻辑（区域库存、阶梯库存规则）由平台自己保证，
  交互路径与人工操作一致，平台风险最低。
  ⚠️ **2026-10-24 二期起主流程改为「先直提」**：startClearStock 先走 stock-direct.js
  直接提交参数（/stock/manage/detail + edit,接口取样参数;区域库存等形态守卫回退）,
  失败才静默回退本点击链路。消息盒子条目格式 =「商品名 + 状态」（用户 2026-10-24 定）。
  渠道品页走 channel-stock.js 的独立接口体系（preview + partial_update,经探针
  页面世界页面侧发起过请求）,与主品接口完全不同——改清零逻辑时两套都要看。

**`main.js` — 入口与开关调度**
- `window.__DYB_INITIALIZED__` 防重复注入
- **「商品库存清零」是否启用完全由 `dybFeatures.clearStock` 决定**：
  - `enableClearStock()` 重置计数并重新扫描注入
  - `disableClearStock()` 先 `stopRowWatcher()` 再 `removeAllClearButtons()`
    —— **顺序不能颠倒**：删按钮这个动作本身会触发 `MutationObserver`，
    先停监听才不会白排一次注入
- 抖店是 **Garfish 微前端架构**，DOM 就绪 ≠ 商品列表已渲染，
  所以 `tryBoot()` 以 1.5 秒间隔最多重试 10 次
- `onRouteChange()` **只注册一次**，回调内部再判断开关状态
  —— 反复开关时注册新回调会让旧回调堆积

**`live/back-to-top.js` / `live/back-to-bottom.js` — 中控台两枚浮动圆钮**
- 右下角两枚 52.8px 白圆钮（上 = 上滑到顶、下 = 下滑到底），半透明常驻、
  悬停实体，水平位置固定 `right: 20px`。
- **只作用于「页面滚动链」，链外的滚动容器一律不碰**（用户 2026-10-14 定）：
  链 = 所有包含 `① 页顶锚点 .container-e6f75f` 或 `② 全页 scrollHeight 最大的
  可滚容器`（实测恒为商品列表容器，约 31752px）的可滚容器，再加 window。
  左边「直播互动」栏的评论列表两者都不含 ⇒ 不在链上 ⇒
  **回顶 / 到底都不得改变它的滚动状态**（用户原话：「无论上滑到顶还是下滑到底，
  都禁止影响到直播互动框的滚动状态」）。改这两枚按钮时**不要退回**「遍历全页
  所有可滚容器」的老写法 —— 那正是 2026-10-14 用户报的 bug（评论被一起归零）。
- 回顶三级路径：页顶锚点（让出 1H）→ 导航头（让出 nav-menu 高度）→ 页面链全部
  归零；三级统一走 `planAlignScroll`（链上除最内层一律归零、最内层承担对齐），
  保证「外层页面容器 + 内层商品容器」两个滚动层同时受控。

**`live/locate.js` — 中控台定位**
- `scrollElementToViewportCenter()` 会**遍历所有可滚动祖先**逐级向外滚动。
  中控台是嵌套滚动结构，只滚内层容器用户看不到任何变化。
- 商品项识别用**结构密度法**：找出「直接子元素中同一 class 出现 3 次以上」的容器。
  纯结构判断，不依赖class 名，平台改版也不易失效。
- **虚拟滚动**：任意时刻 DOM 中只有 8~11 个商品节点，真实有 100+。
  绝不能靠数 DOM 节点判断序号或总数，**必须按行距算位置**：
  ```
  商品数 = 容器内容高 ÷ 行距
  第 N 个位置 = 第 1 个位置 + (N - 1) × 行距
  ```
  行距取多处间距的**中位数**，避免个别商品文本长度差异造成的偏差。
- 呼吸灯高亮：叠加层方式，结束后自动移除，**全程不点击任何商品**，直播中无误触风险

界面只有两处，且都挂在同一个 Shadow 宿主里（`replay-ui.js`）：

  下载中点它 = 开/收详情（用户 2026-10-18 定的形态，别再另做右下角浮窗）。

流程口径（改之前先看）：

- 「整场」判定 = 清单总时长 ÷ 本场时长 ≥ 99%，< 99% 出警告、< 50% 直接阻止；
- **选流三条铁律**（2026-10-18「下到几百兆纯音频」事故后定，改前必读）：
  ① 排序不能只看时长 —— 纯音频清单的时长同样覆盖整场，必须先按「有没有画面」筛；
  ② 选档**先比分辨率、同分辨率才优先 H.264**（`mux.js` 只认它，HEVC 档码率只有一半，
     无脑取最高码率很容易选中 HEVC）；但 1080p 的 HEVC 胜过 720p 的 H.264 ——
     用户明确「我要最高清的」，不能为了好播降清晰度；
  ③ 出确认卡前必须**抓 128KB 看真实轨道**（TS 读 PMT `stream_type`、fMP4 找
     `avc1`/`hvc1`/`soun`），纯音频换候选；**TS+非 H.264 不再拦**，改字节直通、
     原样拼成 `.ts`（2026-10-19 定：用户那场只有一条 H.265 流，拦下等于永远下不了；
     画质零损失，PotPlayer/VLC/剪映能播）。fMP4 的非 H.264 直接直通成 `.mp4`。
     探不到不拦（加密分片 / 不认 Range）。**扩展名必须跟着容器走**（`.ts` / `.mp4`），
     写死 `.mp4` 是骗人，播放器一放就废；
- 先出**确认卡**（场次 / 时长 / 体积 / 清晰度 / 编码 / 文件名可改）再下载，
  成品 MP4；只有「TS + 非 H.264」这种转不了封装的才出 `.ts`（卡上会写明原因与播放器建议）；
- 文件名 `直播回放_2026.10.18_20点13分`（各段用 `_` 连、**整条不留空格**）。
  **2026-10-19 起不再带账号名前缀** —— 用户原话「取消帐号名前缀作为回放的自动生成的名字了」，
  此前抓错三次（「互动指标查看观众分析」/「播前准备」/「我的观众」）。确认卡也不再显示「账号」行；

  在头像容器里**只认「与头像同一行且在其右侧 240px 内」的文本**；再退到按坐标在视口
  右上打网格取点（`elementFromPoint`，按命中格数取胜），再退到「顶栏带 220px 内的
  语义化 DOM → 带标签文案 → 标题」。**位置优先于 class 名**；

必须保留的细节（都是被用户实测打过脸的，别「顺手优化」掉）：

1. **小窗不能「失焦即关」**。旧版监听 `window.blur` 直接 `close()`，用户用
   系统 / 第三方截图工具时窗口必然失焦 → 闪退 → 截图根本贴不进来。现在只有点 X 才关。
2. **小窗截屏要先把自己从画面上拿掉**：`captureScreenshot({hideWindowId})` 内
   `hideWindowForCapture()` 先 `windows.update(state:'minimized')`，再**轮询确认**
   真的成了 `minimized`（部分国产内核会忽略这个请求），没生效就退一步把窗口挪出屏幕
   （`left/top = -32000`）→ 截「非 popup 且未最小化」的焦点窗口 →
   **无论成败都在 `finally` 里还原**（挪过位置就挪回去，再恢复 normal + focused）。
3. **浮层截屏前要把「扩展自己的 UI」全藏起来**（不只是面板本身）—— 见第 11 条。
4. 提交**必须由后台转发**（`dyc:submitFeedback`）：content script 的 fetch 以宿主
   页面为源，云端 REST 网关不响应 OPTIONS 预检 → 页面内直连必被拦。
5. 云端来源校验靠 **DNR 动态规则**把去端点的 `Origin` 改写成 `FB_ENDPOINT` 的域名
   （老内核会给扩展后台请求附 `chrome-extension://<ID>`，网关只放行本应用域名）。
6. 同一标签重复点「反馈」走 `dyc:fbToggle` 复用，不重复注入；注入前先清掉页面里
   遗留的 `#dyc-fb-host`（扩展重载后旧 host 会变成关不掉的幽灵面板）。
7. 降级为小窗时，**失败原因经 URL 的 `why` 参数带过去并显示黄条** ——
   不要让它变成「不知道为什么就变回小窗了」。
8. **提交成功后必须「清空 + 复位」**（2026-10-13 用户报「成功页粘住、清不掉」）：
   `resetForm()` 要清描述 / 联系方式 / 截图 / 类型（回到「功能问题」）、收回成功页、
   恢复表单区与底栏；`open()` 时若发现还停在成功页，也要先复位。
   **只清 `localStorage` 草稿是不够的** —— 面板常驻在页面里，DOM 不复位的话，
   只要标签页不刷新，用户关掉面板、关掉浏览器窗口后再点反馈，看到的还是那张成功页。
9. **截屏时把自己藏起来，必须有兜底恢复**（同日用户报「点完久久不回来」）：
   浮层点截屏会先 `display:none`，恢复**不能只写在 `sendMessage` 回调里** ——
   老内核 / 后台不应答时面板就永久消失了。两边都要挂 9 秒兜底计时器：
   浮层自行恢复显示并提示，小窗自行 `windows.update(state:'normal')` 还原窗口。
10. **小窗不再「提交后自动关」**（与浮层统一为「清空 + 复位 + 留着」），
   所以 `openFeedbackPanel()` 落兜底前要先查有没有已开着的小窗，有就聚焦复用，
   否则用户每点一次反馈就多开一个窗口。
11. **截屏画面里不能有扩展自己的 UI**（2026-10-13 用户报「截图不要截到反馈界面」）：
   藏的范围 = 所有 `dyb-` / `dyc-` 前缀的注入元素（反馈面板 + 大图预览层 +
   左下角 `DY-COCO` 品牌标记 + 历史盒子），做法是 `querySelectorAll` 按前缀找、
   逐个设 `display:none` 并**记下原值**，截完全部还原
   （用内联 style 而不是往 head 插 `<style>`：抖店这类严格 CSP 页面会拦 style-src）。
   **光藏不够，还必须等**：`display:none` 只是改样式，浏览器要等下一次合成才真正
   把它从画面里去掉，而老内核（360 极速浏览器X）的 `captureVisibleTab` 会把
   **「上一帧」交回来** —— 藏完立刻抓，抓到的就是藏起来之前那一帧。所以：
   - 页面侧：`waitPaint()`（双 rAF + 220ms）之后再发消息；
   - 后台侧：浮层路径再等 160ms；抓帧走 `captureVisibleTabSafe()`，它会
     **先无用地抓一次把旧帧顶掉**，隔 140ms 抓第二次，只用第二次的结果；
   - 小窗兜底路径页面里没有浮层在跑，由后台 `chrome.scripting.executeScript`
     注入 `dycHideExtUIInPage` / `dycShowExtUIInPage` 来藏与还原。
   证据 `.tmp/verify-fb-capture.js`：旧版（HEAD）在「旧帧」场景下右上角白像素
   **76.6%**（面板整块入镜），新版 **0%**、绿色底占比 **1.0000**。

**诊断包（`diag`，2026-10-13 新增 · 未推送）**：

**目的**：用户提交反馈时**顺带把「当时的现场」打包上传** —— 环境、开关、扩展控件挂没挂上、
有没有报错、之前点过什么、图是从哪条入口来的。这样助手不用追问「你当时页面长什么样」
就能直接读、直接定位，就像自己在场一样。

采集范围 = **标准档（不碰 DOM 内容）**，共六项，采集内核在 `src/content/diag.js`
（对外 `window.__dycDiag = { note, noteError, snapshot, countText, why, _dump }`）：

| 区块 | 采什么 |
|---|---|
| `env` | 扩展版本 / build、页面 URL（**键名保留、值全打码**：query 与 hash 只留键名，值统一 `***`）、UA、屏幕与视口尺寸、时间戳、采集耗时 |
| `flags` | 各功能开关的当前值 |
| `widgets` | 扩展注入的控件挂载情况：按 `dyb-` / `dyc-` 前缀**自动扫描**（不写死清单，避免过时），按根元素分组，记录 `n` 数量 / `rect` 尺寸 / `pos` 位置 / `disp` 显示 / `z` 层级 / `vis` 可见 / `bad` 异常 |
| `errors` | 报错：**只采扩展自身** —— 内容脚本隔离世界的 `window.onerror` / `unhandledrejection` + 后台 SW 的 `error` / `unhandledrejection`，环形缓冲 ≤ **20** 条 |
| `timeline` | 轨迹：**只记扩展自身的交互**（自己注入的控件被点、开关变更、面板开合），环形缓冲 ≤ **30** 条，单条文本截断 **400** 字符 |
| `shots` | 截图来源：每张图来自哪条入口（`capture` 截屏 / `paste` 粘贴 / `file` 选文件）+ 像素尺寸 |

- **采集时机 = 提交那一刻打快照**；报错与轨迹靠**轻量内存环形缓冲**，
  **不落盘**（刷新即清），代价极低。
- 面板表现：表单末尾一行「**附带诊断信息**」——**勾选框（默认开）+ 汇总一行 + 「查看」展开 JSON**，
  用户可以取消（取消则不采、不上传）。**默认只显示汇总一行**，点「查看」才展开完整 JSON。
- **体积闸门 64KB**：超了按「先砍轨迹 → 再砍控件细节 → 最后砍报错」的顺序削。
  采集总耗时预算 **150ms**（实测 1~6ms），面板侧另有 **1500ms 超时兜底**（拿不到就照常提交）。
- `flags.js` 里有一张 `DYC_DIAG_WIDGET_NAMES` 友好名映射表（20 项）——
  **只用于把控件名显示得好读，不是采集登记表**（采集侧永远是自动扫描）。
- 落库：`feedback` 表新增 **`diag jsonb`** 列（无诊断包时为空对象 `{}`）。
  匿名 REST 是**表级 GRANT**，新列自动跟着可写；jsonb 是**单层编码**
  （`jsonb_typeof = object`，嵌套字段可直接解出，不会双层 `string` 套 `json`）。
- 阅读通道三条：
  1. **日报邮件** —— `scripts/反馈诊断摘要.py --brief` 出精简 3 行版贴进正文；
  2. **会话内图文阅读页** —— `scripts/生成反馈阅读页.py` 内置 `render_diag()`，
     渲染环境 / 开关 / 控件表 / 报错 / 轨迹 / 截图来源六个区块（含截断提示）；
  3. **直接查库** —— 读 `diag` 列（`scripts/反馈诊断摘要.py --items rows.json [--id N]` 也可）。

两条技术边界（**这俩是设计边界，不是 bug，别反复试**）：

1. **隔离世界（isolated world）限制**：内容脚本**看不到抖店页面脚本自己的报错** ——
   跨不过世界边界。所以「报错」这一项只能采扩展自身的；要采页面级 JS 报错必须往
   **`MAIN` world** 注入脚本，**明确不做**（越权、易与平台脚本互相干扰，
   收益不抵风险）。`detectCaps()` 里也已注明「content script 看不到 `chrome.tabs` /
   `declarativeNetRequest` / `offscreen`」属正常的上下文差异，别当成能力缺失去修。
2. **content_scripts 只在页面加载时注入**：扩展更新后，**更新前就已打开的旧标签页**里
   没有 `diag.js`，面板会拿不到数据。因此后台 `injectPanelScript()` 在注入 `panel.js` 时
   **先补注入 `diag.js`**（`files: ['src/content/diag.js', 'src/feedback/panel.js']`；
   老内核的 `tabs.executeScript` 不支持数组，退化成两次单文件调用，**diag 失败不挡面板**）。
   同理，兜底小窗 `feedback.html` 必须在 `feedback.js` 之前**显式** `<script>` 引入
   `../content/flags.js` 与 `../content/diag.js`。

**云端数据（`feedback` 表，2026-10-13 起）**：

**高清原图的两条出口（2026-10-13 用户定：A + C）**：

原图（长边 2400）一直在库里，问题只是「怎么送出去」。两条出口共用同一条
**绕开模型上下文**的取图通道：

1. **A · 日报带高清附件** —— 每天 19:00 的日报除正文内嵌缩略图外，另把原图作为
   **附件**发出。附件名 = `反馈<id>-图<N>.<真实扩展名>`（`<id>` = 该反馈在库里的 id，

   取图落**临时目录** `<cwd>/.tmp/日报图-MMDD/`，**发完信立刻 `rm -rf` 删掉** ——
   本地不留反馈截图仓库（见下「本地磁盘纪律」）。
2. **C · 按需阅读** —— 用户要「看」某条反馈，跑 `scripts/生成反馈阅读页.py` **现场出图文阅读页**

   用 `present_files` 在会话里直接读。**本地不落 jpg**（见下「本地磁盘纪律」）。

取图通道的实现（2026-10-13 建立）：

- 云端数据库函数 `dyc_shot(p_id bigint, p_key text)`，`SECURITY DEFINER`，
  密钥不符抛 `42501`（实测 HTTP 401 `forbidden`）；通过 `/.cloud/database/rest/rpc/dyc_shot`
  以匿名 REST 调用。
- 脚本 `scripts/取反馈原图.py`：读密钥 → 调 RPC → base64 **直接写文件**，
  全程不经过模型上下文（实测 id=21 取回 1920×942 / 231KB）。
  密钥来源：环境变量 `DYC_SHOT_KEY`，否则读**工程上级目录** `.dyc-shot-key`。
- 日报任务里，附件走 **`file_refs`**（先 `agent_mail_upload_attachment` 拿 `file_id`
  再引用，写法是**对象数组** `[{"file_id":"file_xxx"}, …]`）；**严禁**用 `attachments`
  内联 base64 —— 那等于把图片内容塞进模型上下文，照样会炸。
- **单封邮件附件硬上限 = 3 张**（2026-10-13 实测的平台限制）：`file_refs` 给 1/2/3 个都过，
  **第 4 个必被服务端拒**（`Validation failed on field: xmail.SendMessageReq.file_refs`），
  **与体积无关** —— 4 个 6KB 的小图同样被拒。所以日报超过 3 张时按 id 从大到小取，
  其余在正文注明「超出单封 3 张上限，未附」。`file_id` 约 12 小时后过期，须同轮上传 + 发信。

**本地磁盘纪律（2026-10-13 用户明确：「我不需要把反馈图都下载到本地，只需要在本地能够阅读到
相关的反馈内容（图不能丢），不要把我本地当仓库囤积这些截图」）**：

- **本地不留反馈截图**。图永久存在云端 `screenshot_data` 列 —— 只要该条没被标 `已处理`
  且满 90 天，**图就不会丢**；本地一份都不需要有。
- 用户要「读」反馈 → 用 `scripts/生成反馈阅读页.py` 现场生成图文阅读页：
  **原图 base64 只在机器内存里流转、直接内嵌进 HTML，本地不落任何 jpg**；
  产物只有那一份自包含 HTML，按需生成、**同名覆盖、不累积**。
- 用户明确要「拿文件」时（罕见）→ 才跑 `scripts/取反馈原图.py`，且**用完即删**。
- 日报任务取图必须落 `<cwd>/.tmp/日报图-MMDD/` 临时目录，**发完信立刻删除**。
- **禁止**把反馈截图写进 `output/` 或工程目录长期留存（演示产物事后也要清）。

**安全代价（必须记住，别淡化）**：该 RPC 匿名可调，只靠参数里的密钥保护。
**密钥泄露 = 任何人可读取全部反馈截图（含用户屏幕上的私密内容）。**
密钥只存在于三处：工程上级目录 `.dyc-shot-key`（已进 `.gitignore`）、日报任务 prompt、
用户本地 —— **绝不写进扩展源码、`update-manifest.json` 或任何公开页面**。

#### 功能一 · 抖店快捷清空库存按钮

> 适用页面：抖店后台 → 商品 → 商品列表

把「进编辑弹窗 → 找到全部清零 → 点保存」的三步操作压缩为一次点击。

| 能力 | 说明 |
|---|---|
| 行内快捷按钮 | 每个商品行自动注入「清空库存」按钮（半透明常驻，鼠标指向时变实心） |
| 清零前确认 | 弹窗列出商品标题、ID、货号、当前总库存，确认后才执行 |
| 识别失败即拦截 | 无法识别商品的行直接阻止操作，杜绝误点 |
| 零库存前置拦截 | 库存本就是 0 时直接告知，不做无意义的提交 |
| 进度实时反馈 | 执行过程显示「正在清零 3/12」，完成后 3 秒自动消失 |
| 失败结果留存 | 状态消息统一回收，失败详情进入消息盒子 |
| 售罄商品兼容 | 页面布局变化时自动降级定位，按钮不跑位 |
| 动态列表适配 | 翻页、筛选、切换菜单后自动重新注入，无需刷新 |

**执行范围（务必先读）**：清零的是该商品**所有规格的普通库存**；
区域库存（如超市小时达等）**不受影响**；正在直播的商品清零后，直播间将无法继续下单；
**执行不可撤销**。

#### 功能二 · 中控台商品快速定位

> 适用页面：直播中控台（两个入口都支持）
> - 抖店后台 → 直播管理 → 直播中控台（`fxg.jinritemai.com`）
> - 巨量百应 → 达人工作台 → 直播中控台（`buyin.jinritemai.com`）

| 能力 | 说明 |
|---|---|
| 序号直达 | 输入序号点「定位」，滚到对应商品 |
| 整页跟随 | 目标自动落在浏览器视口中央，无需手动再滑 |
| 呼吸灯提示 | 淡橙色呼吸三次，约 3 秒，远处也能看清 |
| 商品总数常显 | 输入框右侧实时显示「共 XXX 个商品」（每秒检查一次） |
| 零误触 | **全程不点击任何商品**，只滚动与高亮 |

只接受**数字序号**，输入非数字会提示「请输入数字序号」；输入框内按回车等同于点「定位」。

**技术说明**：中控台商品列表采用**虚拟滚动**，任意时刻 DOM 中只有可视区的那几个节点，
因此定位不通过「数节点」实现，而是按行距计算位置：

```
商品数 = 容器内容高 ÷ 行距
第 N 个的位置 = 第 1 个的位置 + (N - 1) × 行距
```

行距取多处间距的**中位数**，避免个别商品文本长度差异造成的偏差。
中控台为嵌套滚动结构，定位时会逐级向外滚动所有可滚动祖先，确保目标真正进入浏览器视口。

#### 功能三 · 内置自动更新

> 入口：点击浏览器工具栏的扩展图标 → 弹窗**最下方**

| 能力 | 说明 |
|---|---|
| 静默检查 | 每 6 小时自动查一次仓库上的最新版本标签（**浏览器启动时不查**，避免多浏览器反复发请求） |
| 不打扰 | **图标上不会出现任何红点或数字**，只有主动点开弹窗才看得到提示 |
| 一键安装 | 有更新时「检查更新」变为「安装更新」，点击后弹确认框，确认即自动完成（**点击时会再核对一次最新版**） |
| 自动备份 | 覆盖前完整备份当前版本，**自动保留最近 3 份**（同一版本重复更新只替换那一份） |
| 随时可回退 | 更新**完成后**弹窗版本号旁常驻「回退」入口（有备份才显示），与「有没有新版本」彻底解耦 |
| 完整性校验 | 每个文件都按 sha256 逐一核对，传输损坏或下错版本会被拦下 |
| 只覆盖扩展本体 | 更新只写入 `manifest.json` + `icons/` + `src/`，**不会往用户目录里塞文档或脚本** |
| 看的是「标签」而不是「发行版」 | 检查更新读的是仓库的**标签列表**，不依赖发行版是否建好 |
| 主备双源 | 主源 Gitee，失败自动降级到备用源 GitHub；主源恢复即自动切回 |
| 不受接口限流 | 主源版本查询与文件下载都走 Gitee 网页通道，**不消耗接口额度** |
| 不装任何东西 | 全程在浏览器内完成，不需要外部程序、不写注册表、不要管理员权限 |

**更新是怎么做成的**：扩展在 MV3 下**没有任何文件系统权限**，无法改写自己的文件，
所以「扩展自己更新自己」只有一个出口：**File System Access API**。点「确认安装」后扩展会开一个小窗口：

1. **打开就下载** —— 窗口一打开就开始从仓库拉取本版文件（白名单制），逐个核对 sha256。
   **下载不需要任何权限**，因此与后面的授权操作是**并行**的。
2. **授权写入（通常只需点一下）** —— 首次需选中一次扩展所在目录；之后句柄会被记住，
   浏览器重启后最多点一次「授权并开始」。
3. **备份当前版本** —— 完整快照存起来供回退；备份队列保留**最近 3 份**。
4. **逐文件覆盖** —— `manifest.json` 放到**最后**写，中途失败时磁盘上仍是旧版本号，不会出现半新半旧。
5. 完成后自动重载扩展（**只重载扩展自身**，不关标签页、不重启浏览器）。

> **整个过程用户不需要点「开始更新」**：只要下载完成、权限就绪，它自己就开始覆盖。
> 若目录里已经是这个版本，不会白覆盖一遍，而是直接提示「无需重复覆盖」。

> **为什么每次浏览器重启后可能要重新授权一次？** 这是 Chromium 的安全模型决定的：
> 目录写入权限不跨浏览器会话保留，任何扩展都绕不开。授权只是**一次点击**，不需要重新选择目录。

**浏览器不支持时怎么办**：少数内核没有提供 File System Access 接口。此时弹窗仍能正常检查版本，
更新页会明确提示，并给出手动更新步骤。

#### 功能四 · 中控台全能搜索

升级直播中控台页面**自带的**商品搜索框（不新增控件、不改平台布局），解决平台原生搜索的两个痛点：输款号片段搜不到、不支持多个关键词。

- **款号 / 商品名片段连续匹配**：输 `NE1C0021` 能命中 `NE1C0021W`，大小写无关；款号被页面样式拆断时也有去空白兜底
- **空格分隔多关键词、全部命中才算**：输「粉色 裙」能命中「粉色蛋糕舒适裙 NE1C0021W」，全角空格同样支持
- 命中后自动定位（滚动定位 + 呼吸灯高亮，与「中控台商品快速定位」同一套体验）；多个命中先跳第一个并提示总数，再按回车在命中项之间循环跳；没有结果时滚回原位并如实提示
- **全角 / 半角、大小写自由换算**：输入法打出的「Ａ」「１０８」也能命中 `a`、`108`
- **快扫直达**：约 2 秒扫完整张虚拟列表，搜索框旁有「转圈 + 已扫行数」进度徽标
- **浮动搜索按钮与胶囊搜索框**：滚离原生输入框后，页面正中下方浮现 52.8px 实体搜索按钮；点击后搜索框以按钮为起点**从中心向左右两侧撑开**成胶囊 —— `←` `→` 循环切换命中商品、中间显示 `第X个/总数`、与上方搜索框**双向实时联动**改词、内置「清空」按钮
- **随滚动自动收放**：与回到顶部圆钮**共用同一份判定，同起同落**；点击屏幕外立即收纳回按钮（内容保留）
- 输完按**回车**触发搜索；不点回车不搜索，输入法选词的回车不会误触发
- 纯本地匹配，不上传任何输入内容；空输入、开关关闭、商品列表未加载时完全不接管

#### 功能五 · 中控台快速回到顶部 / 下滑到底

右下角两枚 52.8px 圆形浮动按钮上下相邻（上＝「上滑到顶」、下＝「下滑到底」），**跟随页面缩放**，
水平落在**商品列表滚动条与浏览器最右滚动条之间**（两墙各留 2px 互不接触）。

商品列表滚过第 6 个商品后浮现，点击后**页顶锚点（`container-e6f75f` 元素栏）的顶边落在视口顶下方一个自身高度处，内层商品列表与外层页面同时平滑回到顶部**——中控台是嵌套滚动结构，只滚一层会停在半路；每次点击瞬间实测元素位置与高度再换算，位移逐层精确分摊。回到顶部后按钮自动隐藏。

按钮待命时半透明，鼠标指向时显形并绕一圈细线；悬停提示挂在各自按钮外侧（回顶朝上、下滑到底朝下），互不遮挡。关掉开关按钮即消失，滚动监听一并停止。
