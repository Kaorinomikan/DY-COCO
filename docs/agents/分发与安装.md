## 三之三、分发与安装（2026-10-10 新增，改动前必读）

### 分发物是什么

> ⚠️ **2026-10-11 起，`publish.sh` 不再自动生成分发包**
> （用户要求「推送只更新代码上去 Gitee」，见个性化要求第 8 条）。
> 打包器 `scripts/make-dist.py` **仍然保留**，需要时单独跑：
> ```bash
> C:/Users/79412/.workbuddy/binaries/python/versions/3.13.12/python.exe scripts/make-dist.py
> ```
> 产出 `C:\Develop project\DY-COCO-dist\DY-COCO-v<版本>.zip`。
> 生成规则、包内容、商家侧安装流程（下面两节）**都没有变化**。

包内只有 `manifest.json` / `icons/` / `src/` / `LICENSE`，
加上两个内存生成的文件（`!安装说明.txt`、`!安装助手.bat`）。
`publish.sh`、`AGENTS.md`、`开发日志.md`、`.git` 等开发文件一律不进包。

### 商家侧流程

解压 → 双击 `!安装助手.bat`（自动部署到 `C:\DY-COCO`、把该路径写进剪贴板、
并打开文件夹）→ 浏览器输入 `chrome://extensions` → 打开开发者模式 →
【加载已解压的扩展程序】→ 在选择框按 `Ctrl+V` 回车 → 抖店页面验证左下角绿条。

### 为什么必须是这个流程，不能拖 zip

- 拖 zip 安装时，Chromium 把扩展解到
  `User Data\Default\UnpackedExtensions\<名>_<随机数>\`，
  **每次拖入都是新的随机目录**。这是官方提交
  `[Extensions] Change install directory of .zip file installs` 的有意设计，
  本意是避免解压到临时目录、被系统清理后扩展消失。
- 未打包扩展的 ID = **扩展目录绝对路径的 SHA-256**（`GenerateIdForPath`），
  所以「新目录 → 新路径 → 新 ID」在浏览器眼里就是**一个全新扩展**。
- 后果：`chrome.storage` 里的设置全部丢失（按 ID 隔离）、扩展页出现两个同名
  扩展、两份同时注入导致页面出现两个「清空库存」按钮。
- 而内置更新机制要求扩展目录**固定、可写、用户能找到**。两者不可兼得，
  所以分发方式只能是「解压到固定目录 + 加载已解压」。

> 实测证据：同一份 zip 连拖两次，产生了
> `DY-COCO_33184_1531182569` 与 `DY-COCO_33184_2078689456` 两个目录，内容完全相同。

### 编码约束（改 `install/` 下的文件前必读）

| 文件 | 仓库内保存 | 分发时 | 原因 |
|---|---|---|---|
| `安装说明.txt` | UTF-8 | UTF-8 with BOM + CRLF | 记事本（含老版本）能正确识别 |
| `安装助手.bat` | UTF-8 | **GBK** + CRLF | cmd 默认代码页 936，UTF-8 中文会乱码 |

仓库里存 UTF-8 只为便于阅读和修改，**转码由 `scripts/make-dist.py` 自动完成**，
不要改成在仓库里直接存 GBK（编辑器会把编码搞乱，diff 也不可读）。

> zip 内非 ASCII 条目名按 GBK 写入且**不设 UTF-8 标志位**——
> Windows 资源管理器对无标志位的条目按本地代码页解析，中文文件名才能正常显示。
> Python 回读校验时要按 cp437 → GBK 做对称解码才能拿回原文件名。
> 已用 Windows 自带解压（`Expand-Archive`）实测通过。

### 打包器的两道硬闸门（不要删）

1. 按 `manifest.json` **反查引用完整性**：图标、内容脚本、样式、弹窗、后台脚本，
   缺任何一个直接报错中止。这道闸门专治「icons 没入库就发版」——
   历史上正是它挡下了那个会让扩展直接加载失败的残缺包。
2. 图标必须是真 PNG（校验魔数 `\x89PNG`），防止文本文件误存成 `.png`。

另有三项回读校验：包内不得出现外层目录、不得混入开发文件、
包内 manifest 版本必须与预期一致。

### 发行版上传与下载渠道（⛔ 2026-10-11 起已停用）

> ⛔ **本仓库不再创建 Gitee 发行版。** 依据见「二、用户的个性化要求」第 8 条。
> `publish.sh` 已不再调用 `scripts/gitee-release.py`；该脚本默认模式
> **直接拒绝执行**，必须 `DYC_ALLOW_RELEASE=1` 才放行。
>
> **本节以下内容全部是历史记录**，保留有两个理由：
> ① 万一用户将来要求恢复发行版，可以照着快速重建；
> ② 里面的「Gitee 接口行为」实测结论依然准确可用 ——
> Gitee 的接口与 GitHub 不一样，**不要凭记忆改**。
>
> 当前 `publish.sh` 的终点是「主干与标签已推送且指向同一提交」，
> 不存在原第 9、10 步。

**为什么当年必须单独上传附件，而不能给「标签归档」链接：**
`…/archive/refs/tags/vX.zip` 是源码快照，里面带着 `publish.sh`、`AGENTS.md`、
`开发日志.md` 等内部文件，而且**不含** `!安装说明.txt` 与 `!安装助手.bat`。
把它当下载地址发出去，商家拿到的是残缺包。→ 干净包必须走 Release 附件。

**发给商家的链接必须是「直下链接」，不能是发行版页面链接。**
页面（`…/releases/latest`）上同时挂着三个文件，两个自动生成的源码包名字极像，
面向不懂电脑的商家一定会点错。直下链接只可能下到对的那个。

**已实测的接口行为（Gitee 与 GitHub 不一样，不要凭记忆改）：**

| 事项 | 实测结果 |
|---|---|
| 附件上传 | `POST /repos/{o}/{r}/releases/{release_id}/attach_files`，**用 release_id，不是 tag** |
| 请求格式 | `multipart/form-data`，字段名 `file`；**用 JSON 会失败** |
| 创建发行版 | `POST /repos/{o}/{r}/releases`（tag_name / name / body / target_commitish） |
| 按 tag 查发行版 | `GET /repos/{o}/{r}/releases/tags/{tag}`，**不存在时返回 200 + `null`**（不是 404） |
| 附件下载 | `…/releases/download/{tag}/{文件名}`，**匿名可下载、无需登录**（26.10.10.5 实测：跳 Gitee 签名 CDN，下载物与本地包 sha256 完全一致） |
| 附件下载·探测 | 用 **HEAD** 请求上面这条链接：**附件在 → 首跳 `302` 且 `Location` 含 `attach_files/`**；**不在（含文件名写错）→ `404` + `application/json`**。这是判断「商家能不能下到」最可靠的判据（26.10.10.8 实测） |
| 附件列表 | `GET /repos/{o}/{r}/releases/{release_id}/attach_files`，**必须带 `access_token`**。不带令牌走匿名接口 → `403 Rate Limit Exceeded`，被误读成「附件不存在」（见踩坑第 32 条） |
| 发行版列表 | `GET /repos/{o}/{r}/releases` —— 返回条数可能**少于实际**，且旧发行版会消失（见踩坑第 33 条）。**不要把它当「是否有下载链接」的判据**，要探测直下链接 |
| 发行版页面 | `…/releases/latest` → 302 → `…/releases/tag/{tag}`。**它是页面、不是下载**；页面上除我们的附件外，还有 Gitee 自动生成的两个源码包，名字极像，**别让商家自己去页面里挑** |

> ⚠️ **发行版页面上会有三个文件**（26.10.10.5 实测 `assets` 字段）：
> `DY-COCO-v26.10.10.5.zip`（我们传的干净包）、`v26.10.10.5.zip`、`v26.10.10.5.tar.gz`
> （后两个是 Gitee 自动生成的**源码包**，缺 `!安装助手.bat`、`!安装说明.txt`，
> 却带着 `publish.sh` / `AGENTS.md` / `开发日志.md`）。
> 后两个无法关闭。**所以发给商家一律用「直下链接」，不要给页面链接。**

**令牌**：需要 Gitee 私人令牌（勾选 `projects` 权限）。
脚本按此顺序查找，**绝不写进仓库**：
① 环境变量 `GITEE_TOKEN`；② 工程目录之外的 `C:\Develop project\.dyc-gitee-token`。
`.gitignore` 对 `.dyc-gitee-token` / `*.gitee-token` 做了防御性忽略。

**脚本自带的三道闸门（不要删）**：

1. 分发包必须存在，且**包内 manifest 版本 == 待发布版本**
   —— 防止把上个版本的包当新版发出去（商家装完发现版本没变，极难排查）。
2. 发行版已存在则复用、附件已存在则跳过 → **可反复执行，不会产生重复发行版**。
3. 上传后**探测直下链接**（`…/releases/download/{tag}/{文件名}`）确认商家真能下到。
   ⚠️ **不要用「读附件列表」当判据**：那个接口不带令牌会撞匿名限流，
   返回 403 而被误读成「没有附件」，导致发布明明成功却报失败（见踩坑第 32 条）。

**发行版说明**：优先读仓库根目录的 `RELEASE_NOTES.md`，没有就用 `git log`
自动生成兜底。改了说明重跑脚本即可刷新（走 `PATCH /releases/{id}`）。
写法结构见「五、发布流程 → 版本对比说明的写法」。

### 安装助手的两个测试用环境变量（正式分发不设）

- `DYC_TARGET`：把目标目录改到别处（默认 `C:\DY-COCO`）
- `DYC_SILENT=1`：跳过写剪贴板、打开文件夹、等待按键

两者只为脚本化回归验证用，正式用户不会设置，行为与手动双击完全一致。
