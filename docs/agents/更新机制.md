## 三之二、更新机制（2026-10-10 新增，改动前必读）

### 为什么是这个样子

浏览器扩展在 MV3 下**没有任何文件系统权限**，无法改写自己的文件。
下面这些路都验证过，全部走不通，不要再试：

| 路径 | 结论 |
|---|---|
| `chrome.fileSystem` | 2022 随 Chrome Apps 废弃 |
| `file://` 读写 | CSP + CORS 双重拦截 |
| `chrome.downloads` | 只能落到默认下载目录，不能指定路径，也不能解压 |
| 非商店 CRX + `update_url` 自更新 | Windows 稳定版被 Chrome 拦（M33 起只允许商店源） |
| 外部更新器 / 计划任务 / 原生消息宿主 | **用户明确否决**：不接受在电脑上安装任何更新程序 |

**唯一可行**：File System Access API。由扩展自己的页面调
`showDirectoryPicker()` 拿到扩展目录句柄，直接写入文件，最后
`chrome.runtime.reload()` 让扩展从磁盘重新加载。

### 数据流

```
chrome.alarms（每 6h）  ★ 浏览器启动时**不**检查，只补建定时器
      ↓
service-worker.js ── fetchLatestTag() ──→ Gitee 标签列表 tags.atom（网页通道，不占接口额度）
      ↓  只写 chrome.storage.local 的 dycState
      ↓  ★ 绝不 setBadgeText（用户要求：日常不能有红点）
popup/popup.js ── 读 dycState ──→ 底部「检查更新 / 安装更新」
      │  另:版本号右侧**常驻**「回退」入口(有备份才显示)→ update.html?mode=rollback
      │      （与「有没有新版本」彻底解耦 —— 见下方「回退与备份队列」一节）
      ↓  点「安装更新」时**先强制复查一次**最新标签，再弹确认框
      ↓  （后台状态可能是几小时前查的，期间可能又发版）
      ↓  确认后 chrome.windows.create 开独立窗口
update/update.js
      │
      │ ★ 打开即并行开跑:下载**不需要目录权限**,所以不等授权先下
      ├─ startPrefetch() ── fetchUpdateManifest(tag) 读清单(raw 通道,不占接口额度)
      │     → isExtFile() 白名单 → 必需文件闸门 → 并发 6 路 fetchRawFile()
      │     → 逐个 sha256 校验 → **只留内存,不落盘**
      │     （进度条按**真实字节**走:fetchRawFile 的第 4 参 onChunk）
      │
      └─ 同时 refreshDirUI() 判三态:
            ├ 句柄在 + 权限在   → 「已就绪」→ 预载一完成就**自动写入**
            ├ 句柄在 + 权限没了 → 「待授权」→ 点「授权并开始」＝确认
            └ 句柄失效 / 没有   → 「未定位」→ 选一次目录（startIn 直接定位到上次那个）
      ↓  三条件同时满足才写(预载完成 + 句柄有效 + 权限就绪),且磁盘版本 ≠ 目标版本
      ├─ showDirectoryPicker() 取扩展目录句柄（存 IndexedDB）
      ├─ snapshotDir() 快照当前版本（存 IndexedDB,排除 .git）
      ├─ writeFile() 逐文件覆盖,manifest.json 最后写
      ├─ 回读校验 → chrome.runtime.sendMessage(dyc:markUpdated)
      └─ chrome.runtime.reload()
```

### 回退与备份队列（2026-10-14 新增，改动更新链路前必读）

**为什么单独做一层**：更新页入口只在「发现新版本」时出现（弹窗里 `updateAvailable=true`）。
更新成功后后台把 `updateAvailable` 置回 false，弹窗永久显示「已是最新」，更新页**再也打不开**
—— 而回退按钮挂在更新页上，于是**更新一成功，回退入口就永久消失**（用户 2026-10-13 报障）。
结论：回退入口必须与「有没有新版本」解耦，常驻在弹窗上。

**语义边界（刻意保留的约束）**：
- 更新**进行中**不允许回退 —— 写入阶段中断会留下半新半旧的目录，等于变砖。
- 要保证的语义是「更新完成后，永远留一条回去的路」。

**组件与链路**：

```
src/shared/backup-store.js   ← 弹窗与更新页**同源共用同一个 IndexedDB**（这是弹窗能显示
   │                           回退入口的前提；popup.html 与 update.html 都 <script> 引入）
   ├─ DYC_STORE   IndexedDB kv 原语（get / set / del）
   └─ DYC_BACKUP  备份队列 MAX=3；同版本替换；老单条格式自动包装成数组（不丢用户已有备份）

popup/popup.js
   └─ 版本号右侧常驻 <a id="upd-rollback">「回退」</a>
        有备份才显示，悬停提示可回退版本
        → chrome.windows.create(update.html?mode=rollback)
          （**必须独立窗口**：目录授权框会抢焦点，在弹窗里开不出来）

update/update.js 两种模式
   ├─ ?tag=&version=   升级（原行为不变）
   └─ ?mode=rollback   回退：**不下载、不自动执行** —— 列备份(单选) → 定位目录 →
                       授权 → 点「回退到 vX」→ 写回 → pruneExtraFiles → 回读校验 → reload
```

**回退时为什么必须删文件（`pruneExtraFiles`）**：只把备份里的旧文件写回去，新版本**新增**的
文件会残留在目录里，那不算真正回到上一版。删除严格三重保险：只删 `isExtFile()` 白名单内、
不在备份清单里、**且不删目录**。

**更新失败自动回滚**：写入失败或回读校验不通过时自动调 `restoreSnapshot`（与手动回退**共用
同一条链路**）；自动回滚本身失败，才显示手动回退按钮兜底。

**取证**：`.tmp/verify-rollback.js` —— **25/25**（真实 Chromium 裸 CDP，零 npm 依赖）。

### ⚠️ Service Worker 脚本缓存（改动 `src/shared/` 前必读）

**这是本项目最难查的一个坑，已在 `publish.sh` 里加了机械闸门。**

MV3 的 Service Worker 脚本会被浏览器缓存，**缓存键是主脚本 `service-worker.js`
自身的内容**。被 `importScripts('../shared/gitee.js')` 引入的文件属于同一个
「脚本包」，但它**不参与缓存键的判定**。于是会出现这种组合：

| 磁盘上的 `gitee.js` | `service-worker.js` | 后台实际跑的代码 |
|---|---|---|
| 旧 | 旧 | 旧 |
| **新** | **一个字都没变** | **仍然是旧** ← 就是这里出问题 |
| 新 | 变了 | 新 ✅ |

**2026-10-10 真机事故（360 极速浏览器X）**：

1. 把修复后的 `gitee.js` 拷进 `C:\DY-COCO`，点「重新加载扩展」
2. 弹窗版本号正确显示成新版 —— 因为 manifest 是单独读的，掩盖了问题
3. 但点「检查更新」**仍然报旧代码才有的那句** `Gitee 接口返回 403（/tags?per_page=100）`
4. 查浏览器 `Default\Service Worker\ScriptCache` 的最后写入时间，**早于文件更新时间**
   → 实证脚本包根本没换
5. 给 `service-worker.js` 加一行 `var DYC_BUILD = '…';` 后重新加载，**立刻生效**

**规则：每发一版都必须改掉 `src/background/service-worker.js` 里的
`var DYC_BUILD`**（格式 `<版本号>+swN`）。不是「动了依赖才改」——
`importScripts` 引入的 `gitee.js` / `flags.js` 不参与缓存键判定，
只要主脚本字节不变，浏览器就继续复用整个旧脚本包。

为什么收紧成「每版必变」（2026-11-05 用户实测）：
- 旧闸门只盯 `src/shared/`，而 SW 的第二处 `importScripts` 是
  `../content/flags.js`。它改了、闸门不管、构建号不动 ⇒ 缓存包不重建。
- 表现：弹窗是新代码（认识新开关键）、后台是旧代码（`dycFlagMeta()` 不认）
  ⇒ 点开关得到「设置未保存」，重启浏览器才恢复；
  `chrome.runtime.reload()` 后仍跑旧包 ⇒ 只能去扩展管理页手动「重新加载」，
  四个浏览器就要按四次。

`python scripts/check-sw-build.py --fix` 按当前 manifest 版本改写构建号；
`publish.sh` 用 `--prev-tag` 机械校验「构建号必须与上一标签不同」——不满足直接
中止发布，不靠人记。依赖清单由脚本从源码解析，以后新增 `importScripts` 自动纳入。

> 历史教训：`26.10.10.4` 修的就是检测限流，但那次只改了 `gitee.js`、
> 主脚本一字未动。结果是**全新安装 .4 的用户没问题，从 .3 自更新上来的用户
> 后台仍跑旧代码、照旧 403**。这就是紧接着出 `26.10.10.5` 的原因。

### 数据源与接口（全部实测过）

#### 版本查询：三条通道，标签源优先（`fetchLatestTag()`）

**① 【主通道】`GET …/tags.atom?t=<时间戳>` —— 标签订阅源，含全部标签**

```js
fetch('https://gitee.com/lyrical-adagio/DY-COCO/tags.atom?t=' + Date.now(),
      { redirect: 'follow', cache: 'no-store' })
  → 抠出全部 <title>vX.Y.Z</title>，逐条 compareVersion 取最大
    // fetchLatestTagFromTagsFeed()
```

- **为什么必须是它（26.10.10.7 的事故，见踩坑第 31 条）**：Gitee 上「git 标签」
  与「发行版」是两样独立的东西，`…/releases/latest` 只跟着**发行版**走 ——
  只推标签、没建发行版时，那里根本没有这个版本。实测本仓库（2026-10-10）：
  `/releases` 页面只有 4 个版本，`/tags.atom` 有 9 个（多出的正是 5 个没有
  发行版的标签）。于是一旦出现「标签推成功、发行版没建成」的半发布状态，
  扩展就**永远看不见新版本**，本地 `latestTag` 停在旧值 —— 真机表现是
  「检查更新像在读旧缓存」。
- Atom 订阅源属于**网页通道**，不占接口额度 —— 检测依然是 0 次 API 调用。
- **不依赖条目顺序**（那是按打标签时间排的，不是按版本号排的）：把全部
  `<title>vX.Y.Z</title>` 抠出来，逐条 `compareVersion` 取最大值。
- 带 `?t=` 时间戳是刻意的：标签内容不可变，但「最新是哪一个」会变；
  换 key 可保证任何一层缓存都不会把检测结果卡在旧值上。
- 实测：匿名可取（HTTP 200、`application/atom+xml`、约 18 KB、含全部标签）。

**② 【兜底】`HEAD …/releases/latest` —— 网页路由，不占接口额度**

```js
fetch('https://gitee.com/lyrical-adagio/DY-COCO/releases/latest',
      { method: 'HEAD', redirect: 'follow', cache: 'no-store' })
  → 从 res.url 里抠出版本标签          // fetchLatestTagFromWeb()
```

- 它是**网页路由**，不走 `/api/v5`，所以**不受匿名限流**（未登录 API 只有 60 次/小时，
  见踩坑第 24 条）。这条改造之后，**日常检测是 0 次 API 调用**。
- **必须用 `HEAD`，不能用 `GET`**：`GET` 会因内容协商被导去源码归档
  （`repository/blazearchive/<tag>.zip`），那个 URL 带 `Expires/Signature` 签名参数，
  没法自己拼；`HEAD` 不会真去下归档。
- **落点有两种，正则必须都认**（都是实测到的，见踩坑第 25 条）：
  - `…/releases/tag/<tag>` ← curl 停这里
  - `…/repository/blazearchive/<tag>.tar.gz` ← 部分客户端被导去归档

  落点取决于对方服务器对请求头的内容协商，**不可控**；但两种 URL 里都带版本号，
  所以用宽松正则一起认：`/(?:releases\/tag|blazearchive)\/(v?\d+(?:\.\d+)+)/i`。
- 落点仍在 `gitee.com` 同域内，不跨域，`host_permissions` 的 `https://gitee.com/*`
  已足够，不需要额外放行。
- ⚠️ **它只反映发行版**：看不到「只有标签、没建发行版」的版本 ——
  这正是 26.10.10.7 把它降级为兜底的原因（见踩坑第 31 条）。
- **前置条件：仓库里得存在 Release**。发行版被删光时这里返回 404，
  检测会继续降级到 API，而 API 又可能限流。

**③ 【降级通道】`GET …/api/v5/repos/lyrical-adagio/DY-COCO/tags?per_page=100`**

`fetchLatestTagFromApi()`：取列表里最大的版本标签。
**未登录时 60 次/小时**，超了返回 403 `Rate Limit Exceeded`（带令牌 5000 次/小时），
所以它**只作兜底，不能当常规路径**。

- `per_page=100` 不能省：默认分页会漏掉较新的标签。
- 用 tags 列表取最大值、而不是用某个「最新」接口，是为了兼容
  「只打 tag、不建 Release」的情形。
- 保留它的意义：万一 Release 被删、或网页路由改版，检测不会彻底失灵。

`fetchLatestTag()` 是总入口，三级顺序**不可随意合并**：
`tags.atom`（标签全集）→ `releases/latest`（发行版子集）→ API（受限流）。
把第 2 级放到第 1 级前面，就等于把「纯标签版本看不见」这个坑又踩回去。

#### 文件传输：走 raw 通道（26.10.10.6 从 API 搬过来）

**这是 26.10.10.6 的核心改动。** 老实现走 `/git/trees` 列目录 + `/git/blobs`
取内容，两次线上事故之后判定这条路不可靠：

- 一次更新约 25 次 API 调用（1 次取树 + N 次取 blob），**全部吃匿名额度**；
- 实测（2026-10-10）：额度打满后**所有** API 端点一律 403 —— 连
  `mirrors/nginx` 这类别人的公开仓库也 403，说明是 **IP 级整体限流**，
  不是我们仓库的问题。商家在办公室共享出口 IP（NAT）下可能本来就没额度；
- 真机表现：点「安装更新」→ `更新失败：Gitee 接口访问太频繁被限流了（403）`。

同一时刻 raw 通道**连续 30 次请求全部 200**，`releases/latest` 也正常。于是下载整体改走 raw：

| 步骤 | 请求 | 说明 |
|---|---|---|
| 读清单 | `GET …/raw/<tag>/update-manifest.json` | 1 次，得到 `[{path,size,sha256}]` |
| 取文件 | `GET …/raw/<tag>/<path>` | N 次（本工程 23 个） |

**全程 0 次 API 调用**，从此不受额度影响。

- **为什么需要清单文件**：raw 只能按已知路径取单个文件，**没有列目录的能力**。
  所以要有一份清单告诉扩展有哪些文件、多大、sha256 是多少。
  它由 `scripts/make-update-manifest.py` 生成、随代码提交进仓库根，
  `publish.sh` 里有闸门保证它与代码逐字节对应（见「五、发布流程」）。
- **跨域代价**：`…/raw/…` 会 302 跳到 `raw.giteeusercontent.com`
  （带 `metadata` + `signature` 参数）。所以 `manifest.json` 的
  `host_permissions` **必须放行 `https://raw.giteeusercontent.com/*`**，
  否则请求被 CORS 挡下。这是本次唯一新增的权限，别删。
- **校验改用 sha256**：raw 拿到的就是文件原始字节，直接
  `crypto.subtle.digest('SHA-256')` 即可，不必在 JS 里模拟 git 的对象封装格式
  （老实现要算 `sha1("blob <len>\0" + 内容)`）。清单里的 hash 由 Python
  `hashlib.sha256` 产出，两边格式一致（小写十六进制，实测逐位相同）。
- **清单哈希对应的是「仓库里的内容」，不是工作区**：生成脚本会对文本文件做 LF
  归一化（模拟 git 存储行为，`size` 与 `sha256` 同源）。本机 `core.autocrlf=true`，
  实测曾出现 7 个文件处于 `i/lf w/crlf`，若不归一会让商家更新在这些文件上校验失败。
  详见踩坑第 30 条。
- **失败提示要分情况**：清单 404 说明该 tag 没有清单（只可能是本功能上线前的
  老版本），提示用户改用完整安装包升级 —— 不要笼统报「下载失败」。
- **为什么不用整包 zip**（也考虑过，否决了）：整包只要 1 次请求，但解压要么自己
  实现 zip 解析，要么依赖 `DecompressionStream('deflate-raw')`（Chromium 103+），
  在 360 极速浏览器X / 夸克这类内核版本不透明的分支上不可控；
  且一旦某个文件被浏览器占用，整包覆盖会半途失败、留下半成品。
  逐文件下载还能**精确定位是哪个文件写失败并单独重试**。

### 扩展文件白名单（先过滤，再校验）

`update.js` 用 `isExtFile(path)` 过滤清单，**只放行 `manifest.json` + `icons/` + `src/`**，
其余一律不下载、不写盘。

- 现在是**双保险**：清单（`update-manifest.json`）由生成脚本产出，本来就只含扩展本体；
  更新页仍再过滤一次，防清单被改坏或将来两边口径漂移。
  （历史：老实现是 `fetchTree` 把整棵仓库树拉下来再过滤，`v26.10.10.5` 下 33 个文件里
  12 个是开发文件 —— `AGENTS.md`、`README.md`、`RELEASE_NOTES.md`、`LICENSE`、
  `publish.sh`、`.gitignore`、`.gitee-url.bak`、`开发日志.md`、`install/`、`scripts/`。）
- 用**闭集白名单**（只认这三个前缀），不是列举排除项 —— 将来仓库里新增任何文档、
  脚本、测试目录都自动被挡住，不必每次回来补规则。
- 为什么必须挡：写进去的是**用户的扩展目录**。Chromium 虽然根本不会加载这些文件，
  但它们会永久留在商家机器上，而且会让「目录里哪些才是扩展本体」变得难以分辨。
- **新增扩展需要的顶层目录时（例如将来加 `_locales/`），必须同时改两处**：
  `update.js` 的 `EXT_TOP_DIRS`，以及 `scripts/make-update-manifest.py` 的 `DIRS`。
  只改一处会导致「清单里有但被过滤掉（漏更新）」或「开发文件被写进扩展目录」。
- 清单文件本身（`update-manifest.json`）在白名单之外，所以**不会**被写进扩展目录。

### 完整性与安全闸门（不要删）

1. **必需文件闸门**：包内必须含 `manifest.json` + 三个 `icons/*.png`，缺一即中止。
   （见过一次：图标尚未入库时打出的标签里没有 `icons/`，
   覆盖后 manifest 引用不到图标，扩展**直接加载失败**。宁可不让更新，也不能让扩展变砖。）
2. **sha256 校验**：本地对拿到的字节算 sha256，与清单里记录的比对。
   （老实现是 git blob SHA-1 `sha1("blob <len>\0" + 内容)`，随下载改走 raw 一并换掉。）
   发布时有闸门保证清单哈希与提交的代码一致，所以这层校验同时盯住
   「传输损坏」和「云端被换成别的版本」两种情况。
3. **包内版本号必须等于目标版本**，防下错版本。
4. **目录身份校验**：写入前读目标目录的 `manifest.json`，name 必须含「可可助手」。
5. **先全部下载再写盘**：网络中途失败时磁盘保持原样。
6. **`manifest.json` 最后写**：中途失败时磁盘上仍是旧版本号。
7. **写入后回读校验**：重新读一次磁盘上的 `manifest.json`，版本号不是目标版本
   就判定失败（Windows 上文件被占用时，写入 API 返回成功不代表真的落盘）。

### 已知限制（必须如实告知用户）

- **FSA 的目录写权限不跨浏览器重启保留**（Chromium 只对已安装 PWA 持久化）。
  所以浏览器重启后第一次更新，用户需要点一次「授权写入」。
  句柄存在 IndexedDB 里，**不需要重新翻目录**。
- **回滚只恢复旧文件，不删除新增文件**。
- 本机没有 Chrome / Edge，实际使用 360 极速浏览器X 与夸克，
  FSA 支持情况需真机验证；不支持时更新页会降级为引导式手动更新。

- ⚠️ **「自动扫描候选路径」做不到,别再去试。** 原规划里写过
  「候选路径扫描(如 `C:\DY-COCO`)」—— 浏览器的安全模型**不允许 JS 按绝对路径
  访问磁盘**,`showDirectoryPicker()` 也不接受路径参数(只吃 `FileSystemHandle`)。
  能做的只有两层:① 复用 IndexedDB 里记的句柄;② 真要重选时把上次的句柄当
  `startIn` 传给对话框,系统会直接打开那个目录。见「开发日志.md → 计划十一」。

  ✅ **替代做法(2026-10-11 已落地)**:既然**做不到自动定位,就把话说清楚** ——
  第 1 步在「未定位 / 句柄失效」时显示一段提示,写明
  「默认目录 `C:\DY-COCO`(安装助手的固定目标)」并保留「目录里能看到
  `manifest.json`」这个用户可自核的判据,另配一个「复制默认路径」小按钮。
  相关元素:`#dir-default`(提示行)、`#btn-copy-dir`(按钮)、
  `DEFAULT_DIR_HINT`(常量,**只用于文案,不参与任何逻辑判断**)。
  ⚠️ 文案必须带条件「如果你用的是安装助手」—— 用户可能手动存到别处,硬写会误导。

### 用户对更新功能的硬性要求（不可违背）

1. **弹窗「其他」组的最下方**依次是:版本号 + 检查更新、项目地址(Gitee 超链接)。
   该组内顺序固定为 **调试模式开关 → 调试提示 → 更新区**(2026-10-11 用户把调试模式
   从「抖店」迁进来),因此「检查更新」恒为全弹窗最末一行,不会因更新状态变化而上下浮动。
2. **每 6 小时**自动检查一次（2026-10-11 由 24 小时改为 12 小时、再改为 6 小时）；
   查到更新后「检查更新」文字变「安装更新」
3. **浏览器启动时不做检查**（2026-10-11 用户定）。理由：用户日常同时开
   四个以上浏览器，每个浏览器每次启动都查一遍会造成大量无谓请求，
   而这些请求用户根本感知不到（提示只在主动点开弹窗时才显示）。
   → 启动时只补建定时器；且重建定时器的首次触发点排在「上次检查 + 6 小时」，
   不允许因为重启而让检查提前。
4. 点「安装更新」→ **先强制复查一次最新标签**，再弹确认/取消对话框
   → 确认后自动安装。复查的意义：弹窗依据的后台状态可能是几小时前查的，
   期间 Gitee 上可能又发了新版本；不复查就会装到「上次查到的那个版本」，
   而不是点击这一刻的最新版。
5. **日常使用绝对不能在扩展图标上出现红点**。只有点开弹窗才能看到提示，
   且不做图标徽标（2026-10-10 用户从「小圆点 / 数字 / 不做」三选一中选了**不做徽标**）
6. **禁止在电脑上安装任何更新程序**（否决了外部更新器、计划任务、原生消息宿主）
7. **更新过程要尽可能少点**(2026-10-11 用户提「太繁琐」后落地,计划十一):
   下载与授权并行(窗口一开就下)、预载完成 + 权限就绪即自动覆盖、
   状态行直显三态、可恢复错误自动重试一次。
   但「覆盖」这个动作必须有一次显式的用户确认 —— 那一下由 FSA 的授权点按充当
   (`requestPermission` 必须由用户手势触发,这是平台硬约束)。
